用 Docker Compose 搭建 Prometheus + Grafana 监控栈

Docker

用 Docker Compose 搭建 Prometheus、Alertmanager、Grafana 与 cAdvisor 监控栈，包含抓取配置、告警规则、仪表盘自动装载和容量规划

标签：
Docker Compose Prometheus Grafana 监控告警
发布于 2026年11月22日

前言 ​

一套最小可用的监控栈有四个组件：

  • Prometheus：按固定间隔拉取指标，写入本地时序库，按规则计算告警。
  • Exporter：把目标系统的指标翻译成 Prometheus 能抓的 HTTP 接口，例如 node-exporter、postgres-exporter、cAdvisor。
  • Alertmanager：接收 Prometheus 推来的告警，做分组、抑制、静默和路由。
  • Grafana：查询 Prometheus 并展示，数据源和仪表盘可以通过文件自动装载。

这四部分用 Compose 串起来，配置文件都放在宿主机目录，容器重建不会丢。

目录结构 ​

text

compose.yaml ​

yaml
name: monitoring

services:
  prometheus:
    image: prom/prometheus:v3.16.0
    restart: unless-stopped
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --storage.tsdb.path=/prometheus
      - --storage.tsdb.retention.time=15d
      - --storage.tsdb.retention.size=20GB
      - --web.enable-lifecycle
    volumes:
      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - ./prometheus/rules:/etc/prometheus/rules:ro
      - ./prometheus/app_metrics_password:/etc/prometheus/app_metrics_password:ro
      - prometheus-data:/prometheus
    ports:
      - "127.0.0.1:9090:9090"
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "5"

  alertmanager:
    image: prom/alertmanager:v0.35.0
    restart: unless-stopped
    command:
      - --config.file=/etc/alertmanager/alertmanager.yml
      - --storage.path=/alertmanager
    volumes:
      - ./alertmanager/alertmanager.yml:/etc/alertmanager/alertmanager.yml:ro
      - alertmanager-data:/alertmanager
    secrets:
      - smtp_password
    ports:
      - "127.0.0.1:9093:9093"

  grafana:
    image: grafana/grafana:13.3.1
    restart: unless-stopped
    environment:
      GF_SECURITY_ADMIN_USER: admin
      GF_SECURITY_ADMIN_PASSWORD__FILE: /run/secrets/grafana_admin_password
      GF_USERS_ALLOW_SIGN_UP: "false"
      GF_ANALYTICS_REPORTING_ENABLED: "false"
      GF_SERVER_ROOT_URL: http://localhost:3000
    secrets:
      - grafana_admin_password
    volumes:
      - grafana-data:/var/lib/grafana
      - ./grafana/provisioning:/etc/grafana/provisioning:ro
      - ./grafana/dashboards:/var/lib/grafana/dashboards:ro
    ports:
      - "127.0.0.1:3000:3000"

  node-exporter:
    image: prom/node-exporter:v1.13.1
    restart: unless-stopped
    command:
      - --path.procfs=/host/proc
      - --path.sysfs=/host/sys
      - --path.rootfs=/host/root
    pid: host
    volumes:
      - /proc:/host/proc:ro
      - /sys:/host/sys:ro
      - /:/host/root:ro,rslave
    ports:
      - "127.0.0.1:9100:9100"

  cadvisor:
    image: ghcr.io/google/cadvisor:v0.61.1
    restart: unless-stopped
    privileged: true
    devices:
      - /dev/kmsg
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:rw
      - /sys:/sys:ro
      - /var/lib/docker/:/var/lib/docker:ro
      - /dev/disk/:/dev/disk:ro
    ports:
      - "127.0.0.1:8080:8080"

secrets:
  grafana_admin_password:
    file: ./secrets/grafana_admin_password.txt
  smtp_password:
    file: ./secrets/smtp_password.txt

volumes:
  prometheus-data:
  alertmanager-data:
  grafana-data:

cAdvisor 的镜像从 0.53 起迁到了 ghcr.io/google/cadvisor，旧文档里的 gcr.io/cadvisor/cadvisor 只适用于更早的版本。它需要读取宿主机的 cgroup、Docker 数据目录和内核日志，因此挂了 privileged 和 /dev/kmsg。

prometheus.yml ​

yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s
  external_labels:
    env: production

rule_files:
  - /etc/prometheus/rules/*.yml

alerting:
  alertmanagers:
    - static_configs:
        - targets:
            - alertmanager:9093

scrape_configs:
  - job_name: prometheus
    static_configs:
      - targets: ["prometheus:9090"]

  - job_name: node
    static_configs:
      - targets: ["node-exporter:9100"]

  - job_name: cadvisor
    static_configs:
      - targets: ["cadvisor:8080"]

  - job_name: app
    metrics_path: /actuator/prometheus
    basic_auth:
      username: metrics-reader
      password_file: /etc/prometheus/app_metrics_password
    static_configs:
      - targets: ["app:8080"]

字段的作用：

字段说明
scrape_interval抓取间隔，15s 是常见起点；目标多时不要一味调小
evaluation_interval告警规则计算间隔
external_labels写到每条时间序列上的附加标签，跨集群汇总时用来区分来源
metrics_path指标路径，Spring Boot Actuator 是 /actuator/prometheus
basic_auth抓取需要认证的端点；password_file 避免把密码写进配置文件

应用不在同一个 Compose 网络里时，把 targets 换成实际地址。Linux 上抓宿主机端口需要：

yaml
    extra_hosts:
      - "host.docker.internal:host-gateway"

然后用 host.docker.internal:8080。Docker Desktop 默认支持这个域名。

告警规则 ​

prometheus/rules/availability.yml：

yaml
groups:
  - name: availability
    rules:
      - alert: TargetDown
        expr: up == 0
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.job }} 抓取失败"
          description: "{{ $labels.instance }} 已持续 2 分钟无法抓取。"

      - alert: HighMemoryUsage
        expr: |
          (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) > 0.9
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "宿主机内存使用率超过 90%"
          description: "当前使用率 {{ $value | humanizePercentage }}。"

      - alert: ContainerRestarting
        expr: |
          changes(container_start_time_seconds[10m]) > 0
        for: 0m
        labels:
          severity: info
        annotations:
          summary: "容器 {{ $labels.name }} 发生重启"

for 表示条件持续多久才真正触发，避免瞬时抖动产生告警。up == 0 是最基础的可用性规则，但要先确认目标本来就应该在线，否则维护窗口会一直报警。

规则写完后用 promtool 校验，别等 Prometheus 启动失败再回头找：

bash
docker compose exec prometheus promtool check rules /etc/prometheus/rules/availability.yml

Alertmanager ​

alertmanager/alertmanager.yml：

yaml
global:
  resolve_timeout: 5m

route:
  receiver: default
  group_by: [alertname, job]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

receivers:
  - name: default
    email_configs:
      - to: ops@example.com
        from: alertmanager@example.com
        smarthost: smtp.example.com:587
        auth_username: alertmanager@example.com
        auth_password_file: /run/secrets/smtp_password
        require_tls: true

group_by 决定哪些告警合并成一封通知；repeat_interval 控制未恢复告警的重复提醒频率。邮件只是最省事的通道，实际使用中 Webhook 接企业微信、钉钉、Slack 更常见，receivers 里换成 webhook_configs 即可。

Grafana 自动装载 ​

数据源 grafana/provisioning/datasources/prometheus.yml：

yaml
apiVersion: 1

datasources:
  - name: Prometheus
    uid: prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true
    jsonData:
      timeInterval: 15s

仪表盘提供者 grafana/provisioning/dashboards/default.yml：

yaml
apiVersion: 1

providers:
  - name: default
    orgId: 1
    folder: ""
    type: file
    disableDeletion: false
    updateIntervalSeconds: 30
    allowUiUpdates: false
    options:
      path: /var/lib/grafana/dashboards
      foldersFromFilesStructure: false

把从 grafana.com 下载的 dashboard JSON 放进 grafana/dashboards/，重启后自动出现。allowUiUpdates: false 表示 UI 上的修改不会被保存，配置以文件为准，避免“界面上调好的图在下次重建后消失”。

面板里引用数据源时用 uid（上面的 prometheus）而不是名字，重命名数据源不会把面板打断。

验证 ​

bash
# 配置语法
docker compose exec prometheus promtool check config /etc/prometheus/prometheus.yml

# 服务和抓取目标
curl -fsS http://localhost:9090/-/ready
curl -fsS http://localhost:9090/api/v1/targets | head -c 500

# 热加载配置（需要 --web.enable-lifecycle）
curl -X POST http://localhost:9090/-/reload

# Grafana
curl -fsS http://localhost:3000/api/health

打开 http://localhost:9090/targets，确认每个 job 都是 UP。如果某个 exporter 显示 DOWN，先看 Prometheus 的报错：connection refused 是端口或网络不对，context deadline exceeded 多半是目标太慢或被防火墙丢弃，401 则是 basic_auth 配置不匹配。

数据库与中间件 exporter ​

常见 exporter 及关键配置：

目标镜像关键配置
PostgreSQLprometheuscommunity/postgres-exporter:v0.21.1DATA_SOURCE_NAME=postgresql://user:CHANGEME@db:5432/app?sslmode=disable
MySQLprom/mysqld_exporter:v0.21.0DATA_SOURCE_NAME=user:CHANGEME@(db:3306)///
Redisoliver006/redis_exporter:v1.98.0REDIS_ADDR=redis://redis:6379，密码用 REDIS_PASSWORD
Nginxnginx/nginx-prometheus-exporter需要 nginx 开启 stub_status，用 --nginx.scrape-uri 指定

以 PostgreSQL 为例：

yaml
  postgres-exporter:
    image: prometheuscommunity/postgres-exporter:v0.21.1
    restart: unless-stopped
    environment:
      DATA_SOURCE_NAME: postgresql://exporter:CHANGEME@db:5432/app?sslmode=disable
    ports:
      - "127.0.0.1:9187:9187"

exporter 的连接串里带密码，用 env_file 单独存放并限制文件权限，或者把连接串写进文件再通过启动脚本读取。exporter 只需要只读权限，数据库侧单独建监控账号，不要复用业务账号。

容量与保留 ​

Prometheus 的磁盘占用取决于序列数量和抓取频率，没法给一个通用数字。可行的做法是：

  1. 先按 15s 抓取、保留 15 天上线。
  2. 观察 prometheus_tsdb_storage_blocks_bytes 的增长速度。
  3. 按实际增长反推保留天数，或者用 --storage.tsdb.retention.size 设硬上限。

retention.time 和 retention.size 同时设置时，先到哪个就按哪个删除。指标基数失控（比如把用户 ID、请求 ID 做成标签）会让磁盘和内存一起爆掉，这类标签要在应用侧就排除。

常见问题 ​

现象原因处理
target 一直 DOWN，报 no such host容器不在同一网络，服务名解析不到接入同一网络，或改用可路由地址
target DOWN，报 connection refused端口写错或 exporter 没监听 0.0.0.0检查 exporter 的监听地址和 compose 端口
cAdvisor 只有宿主机数据Docker Desktop 里 cAdvisor 看到的是 Linux VM这是架构限制，容器指标改用 Docker Desktop 自带监控或部署到 Linux 主机
Grafana 面板显示 No data数据源 URL 写成 localhost容器内用服务名 http://prometheus:9090
修改配置后不生效没有触发热加载执行 POST /-/reload 或重启容器
告警不发邮件Alertmanager 路由或 SMTP 认证失败看 Alertmanager 日志和 /-/ready 页面
磁盘增长过快高基数标签或抓取过密减少标签、拉长间隔、设置 retention.size

Prometheus、Grafana 都只绑定在 127.0.0.1，需要远程访问时用反向代理加认证，不要把 9090 直接暴露到公网：Prometheus 的 API 没有鉴权，/-/reload 和 /api/v1/admin 是直接的管理入口。
