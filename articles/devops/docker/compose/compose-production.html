Docker Compose 生产化配置清单

Docker

从健康检查、启动顺序、资源限制、日志轮转、最小权限、密钥管理到一次性任务，整理一份可直接套用的 Compose 生产化配置清单

标签：
Docker Compose 健康检查 资源限制 日志轮转 安全加固
发布于 2026年11月22日

前言 ​

docker compose up -d 能把容器拉起来，不代表这套服务可以长期运行。Compose 的默认值更偏向本地开发：日志不限大小、容器以 root 运行、没有健康检查、密码直接写在 environment 里、一次性任务被 restart: always 反复拉起。

下面按服务从“能跑”到“能运维”的顺序，过一遍容易漏掉的配置。示例以 Linux 主机上的 Docker Engine + Compose v2 为前提。

一个可直接套用的模板 ​

目录结构：

text
deploy/
├── compose.yaml
├── .env
├── .env.example
├── secrets/
│   └── db_password.txt
├── config/
│   └── app.yaml
└── data/
    └── postgres/

compose.yaml：

yaml
name: demo

services:
  db:
    image: postgres:18-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: app
      POSTGRES_DB: app
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    volumes:
      - ./data/postgres:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    stop_grace_period: 30s
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "5"

  migrate:
    image: example/app:1.4.2
    command: ["/app/migrate"]
    restart: "no"
    depends_on:
      db:
        condition: service_healthy
    secrets:
      - db_password

  app:
    image: example/app:1.4.2
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
      migrate:
        condition: service_completed_successfully
    environment:
      DB_HOST: db
      DB_PASSWORD_FILE: /run/secrets/db_password
      TZ: Asia/Shanghai
    secrets:
      - db_password
    ports:
      - "127.0.0.1:8080:8080"
    read_only: true
    tmpfs:
      - /tmp
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    init: true
    mem_limit: 512m
    cpus: 1.0
    pids_limit: 256
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8080/health"]
      interval: 15s
      timeout: 3s
      retries: 3
      start_period: 20s
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "5"

secrets:
  db_password:
    file: ./secrets/db_password.txt

name 决定 Compose 项目名，也就是容器名、网络名和数据卷名的前缀。不同项目在同一台主机上默认会加上各自的目录名，显式指定可以避免重名和误删。

重启策略与优雅停止 ​

取值行为适用
no（默认）退出后不重启迁移、初始化、批处理任务
on-failure非 0 退出码才重启，可配最大次数可能因临时错误退出的任务
always总是重启，包括手动停止后不建议用于需要手动维护的服务
unless-stopped总是重启，但手动停止后保持停止常驻服务，推荐默认值

stop_grace_period 默认只有 10 秒。数据库、消息队列这类需要刷盘和断连的服务通常不够，建议 30 秒以上，并确认应用能处理 SIGTERM：收到信号后停止接收新请求、处理完存量请求再退出。

init: true 会给容器加一个极小的 init 进程作为 PID 1，负责回收僵尸进程并正确转发信号。业务进程自己不会处理 SIGTERM 时，这一项能避免“停容器等 10 秒再 SIGKILL”。

健康检查 ​

yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U app -d app"]
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 30s
参数含义
test退出码 0 为健康，1 为不健康，2 为保留值
interval两次检查的间隔
timeout单次检查超时，超过按失败计
retries连续失败多少次后标记为 unhealthy
start_period启动宽限期，期间的失败不计入 retries

容易出问题的地方：

  • 检查命令必须存在于镜像里。很多精简镜像（distroless、scratch、部分 alpine 变体）没有 curl，写了 curl -f 只会一直 unhealthy。优先用服务自带的客户端（pg_isready、redis-cli ping），或者用镜像里确定存在的 wget。
  • CMD 形式不经过 shell，不能写管道和 &&；需要 shell 特性时用 CMD-SHELL。
  • 健康检查只改变容器状态，不会触发重启。容器 unhealthy 后仍然在跑，需要外部组件（如 autoheal）或编排系统处理。这一点和 Kubernetes 的 liveness probe 不同。
  • start_period 内的失败不算数，适合 JVM、数据库这类启动慢的服务；不要靠把 retries 调大来掩盖启动问题。

启动顺序 ​

depends_on 有两种写法，语义完全不同：

yaml
# 短写法：只保证启动先后，不等待就绪
depends_on:
  - db

# 长写法：等待依赖达到指定状态
depends_on:
  db:
    condition: service_healthy
  migrate:
    condition: service_completed_successfully

可用的 condition：

condition含义
service_started依赖容器已启动（等价于短写法）
service_healthy依赖的健康检查通过
service_completed_successfully依赖以退出码 0 结束，适合迁移、初始化任务

即使写了 service_healthy，也只代表“依赖当时可用”。数据库重启、网络抖动仍会让应用连不上，应用侧的重试和连接池探活不能省。反过来，把启动顺序当作可用性保证，是生产环境常见的一类误判。

一次性任务用 restart: "no"，并且要保证可重复执行：迁移脚本先查版本号再决定是否执行，建桶脚本先判断资源是否存在。否则每次 up 都会重复跑一遍。

资源限制 ​

Compose v2 在 service 级别直接支持：

yaml
mem_limit: 512m
cpus: 1.0
pids_limit: 256
  • mem_limit 是硬限制，超过会触发 OOM Killer，容器退出码为 137。它不会让进程变慢，只会杀掉进程，所以 JVM 的堆上限要留出堆外内存：容器限制 512m 时，-Xmx 给 320m 左右比较稳妥，或者直接用 -XX:MaxRAMPercentage=70 让 JVM 读取 cgroup 限制。
  • cpus 是 CPU 配额，1.0 表示一个核的时间片；超卖时表现为变慢而不是被杀。
  • pids_limit 限制进程和线程总数，能挡住 fork 炸弹和线程泄漏。设置时要大于应用的线程池总和，否则会出现莫名其妙的 Resource temporarily unavailable。

deploy.resources.limits 是 Swarm 的写法，Compose v2 也能读取。同一服务只保留一种写法，两套混写会让实际生效的限制难以判断，排查时很浪费时间。本文统一用 service 级字段。

日志 ​

默认的 json-file 驱动不限制大小，一个死循环打日志的服务可以在几小时内写满磁盘。最低限度要加轮转：

yaml
logging:
  driver: json-file
  options:
    max-size: "20m"
    max-file: "5"

上面的配置表示单个文件 20MB、最多保留 5 个，合计上限约 100MB。日志量大时改用 local 驱动，它默认就带轮转和压缩：

yaml
logging:
  driver: local
  options:
    max-size: "50m"
    max-file: "3"

docker compose logs 对这两种驱动都有效。需要把日志送到 Loki、Elasticsearch 时再换 loki、fluentd 等驱动，但要注意这些驱动通常是插件，节点上没装就会启动失败。

轮转之后，历史日志不会再出现在 docker logs 里。需要长期检索就接入日志系统，别指望 docker logs 当归档。

最小权限 ​

yaml
read_only: true
tmpfs:
  - /tmp
cap_drop:
  - ALL
security_opt:
  - no-new-privileges:true
user: "1000:1000"
  • read_only 把容器根文件系统挂成只读。应用如果要在根目录写缓存、上传临时文件，会直接报 Read-only file system，所以要配合 tmpfs 或单独的可写卷。这一项能缩小被写入 webshell 后的影响面。
  • cap_drop: ALL 丢掉全部 Linux capabilities，需要绑定 80 端口时再单独 cap_add: [NET_BIND_SERVICE]。绝大多数业务容器不需要任何 capability。
  • no-new-privileges 阻止通过 setuid 程序提权。
  • user 指定非 root 运行。注意宿主机上的挂载目录也要相应 chown，否则容器内写不进去。

还有两条不属于 compose 字段，但同样重要：

  • 不要挂载 /var/run/docker.sock。挂进去等于把宿主机 root 权限交给容器，CI、构建类服务尤其要避免；需要构建能力时用 rootless 构建或独立的构建节点。
  • 管理端口只绑回环地址：127.0.0.1:9090:9090。数据库、Prometheus、管理后台都不应该直接暴露在公网，需要外部访问时统一走反向代理并加认证。

配置与密钥 ​

三种注入方式的选择：

方式是否进入容器环境变量是否出现在 docker inspect适用
environment是是非敏感配置
env_file是是一组非敏感配置
secrets否，挂载为文件否密码、Token、私钥

secrets 在非 Swarm 的 Compose 里同样可用，内容以文件形式挂到 /run/secrets/<name>：

yaml
secrets:
  db_password:
    file: ./secrets/db_password.txt

services:
  app:
    secrets:
      - db_password

应用要支持从文件读取，例如 PostgreSQL 镜像的 POSTGRES_PASSWORD_FILE。不支持 _FILE 的应用，可以在启动脚本里 export DB_PASSWORD="$(cat /run/secrets/db_password)"，但这样密码仍会进入进程环境，只是不再出现在 compose 文件和 inspect 里。

Compose 的 secrets 只是“不放进环境变量”，文件本身没有加密。宿主机上要 chmod 600，不要提交到 Git；secrets/ 应该写进 .gitignore。

必填变量用 :? 语法在编排阶段就报错，避免容器起来后才发现变量为空：

yaml
environment:
  DB_PASSWORD: ${DB_PASSWORD:?set DB_PASSWORD in .env}

.env 只负责 Compose 文件的变量插值，不会自动变成容器内的环境变量；要进容器必须显式写 environment 或 env_file。这一点在排查“为什么容器里读不到变量”时容易被忽略。

构建参数（build.args）会留在镜像历史里，不要把密钥放进去。需要构建期密钥时用 BuildKit 的 --secret。

一次性任务与初始化 ​

除了前面的 migrate 服务，常见的初始化动作还有建数据库、建对象存储桶、修目录权限。建议单独放一个任务服务，并用 profiles 控制它不被日常 up 拉起。下面的命令换成自己的初始化工具，关键是支持重复执行：

yaml
  init-storage:
    image: example/app:1.4.2
    command: ["/app/init-storage", "--if-missing"]
    env_file:
      - .env
    profiles:
      - init
    restart: "no"

执行：

bash
docker compose --profile init run --rm init-storage

profiles 里的服务不会在 docker compose up 时启动，只有显式带 --profile 才会参与。初始化逻辑要自带存在性判断：表已存在就跳过，桶已存在就复用，任务才能安全重跑。

需要“应用启动前必须完成”的任务，用 service_completed_successfully 串起来：

yaml
  app:
    depends_on:
      migrate:
        condition: service_completed_successfully

迁移失败时应用不会启动，docker compose up 也会返回非 0。这比“应用先起来、迁移在后台慢慢跑”更容易发现问题。

镜像与构建 ​

  • 固定版本：image: example/app:1.4.2 比 :latest 可复现。要求更严格时固定 digest：example/app@sha256:...，tag 只是给人看的，digest 才是内容。
  • pull_policy：默认 missing（本地没有才拉）。需要每次部署都确认最新镜像时用 always；离线环境用 never，配合本地导入的镜像。
  • 构建时把基础镜像也固定到 digest，避免上游重新打 tag 导致构建结果漂移。
  • 多架构镜像（arm64/amd64）在 build 里声明 platforms，或者用 buildx 一次构建多份。

示例里用了 postgres:18-alpine 这类 minor 标签方便阅读；生产环境应固定到具体补丁版本或 digest。

网络 ​

Compose 会为项目创建一个默认网络，服务名可以直接当 DNS 名用：应用连 db:5432，不需要知道容器 IP。需要隔离时拆成多个网络：

yaml
services:
  proxy:
    networks: [frontend, backend]
  app:
    networks: [backend]
  db:
    networks: [backend]

networks:
  frontend:
  backend:

只有 proxy 同时接入两个网络，数据库就不会出现在 frontend 上。对外只发布 proxy 的端口。

固定 IP（ipv4_address）只在确实需要时使用，比如对接只认 IP 的旧系统。它会带来子网冲突和迁移成本；能用服务名解析就不要写 IP。跨 Compose 文件共享网络时用 external: true，并提前创建网络：

bash
docker network create shared-net

容器里的 localhost 指容器自己。要访问宿主机上的服务，Linux 上加 extra_hosts：

yaml
extra_hosts:
  - "host.docker.internal:host-gateway"

Docker Desktop 默认就带这个域名，Linux 上需要显式声明。

验证清单 ​

部署前先让 Compose 自己检查语法和变量插值：

bash
docker compose config --quiet
docker compose config

启动并等待健康检查通过：

bash
docker compose up -d --wait
docker compose ps

逐项确认：

bash
# 健康状态
docker compose ps --format 'table {{.Name}}\t{{.Status}}'

# 资源占用
docker stats --no-stream

# 最近日志
docker compose logs --since 15m app

# 容器内实际生效的限制
docker inspect --format '{{.HostConfig.Memory}} {{.HostConfig.NanoCpus}}' "$(docker compose ps -q app)"

检查项：

常见问题 ​

现象原因处理
容器一直 unhealthy镜像里没有 healthcheck 用的命令换成镜像内自带的客户端，或安装对应工具
应用启动时连不上数据库只写了短写法的 depends_on改用 condition: service_healthy，并在应用侧重试
迁移容器反复重启restart 不是 no一次性任务必须设 restart: "no"
Read-only file system开了 read_only 但应用要写盘加 tmpfs 或挂载可写卷
Permission denied 写挂载目录宿主机目录属主与容器 UID 不一致chown 到对应 UID，或在 compose 里指定 user
容器里访问 localhost 失败localhost 是容器自己用服务名或 host.docker.internal
退出码 137超过 mem_limit 被 OOM Kill调大限制或降低 JVM 堆
docker compose up 报变量为空.env 不在项目目录或变量名拼错用 docker compose config 查看渲染结果
两个项目互相覆盖容器项目名相同在文件顶部设置 name，或用 -p 指定

Compose 文件顶部的 version 字段已经废弃，写不写都不影响行为，新文件直接省略即可。
