用 Docker Compose 部署 PostgreSQL + pgvector

Docker

用 Docker Compose 部署带 pgvector 的 PostgreSQL，覆盖镜像构建、扩展启用、向量索引、外部配置、备份与升级

标签：
Docker Compose PostgreSQL pgvector 向量检索 数据库
发布于 2026年11月22日

前言 ​

向量检索不一定非要单独的向量数据库。数据量在千万级以内、又需要和业务表做 JOIN、过滤、事务时，把 embedding 直接存进 PostgreSQL，用 pgvector 建 HNSW 或 IVFFlat 索引，通常比再维护一套系统省事。

官方 postgres 镜像不带 pgvector。拿到带扩展的镜像有两条路：用 pgvector 项目维护的预构建镜像，或者从官方 postgres 镜像加 PGDG 的扩展包自己构建。前者省事，后者能固定 PostgreSQL 补丁、扩展版本和基础镜像 digest。下面以自建为主，预构建作为替代。

两种镜像来源 ​

方式镜像好处代价
预构建pgvector/pgvector:0.8.7-pg18-trixie直接 docker pull，不用构建PostgreSQL 补丁和扩展版本跟随镜像维护者
自建postgres:18.6-trixie + PGDG 包基础镜像 digest、PG 版本、扩展包版本都能固定多一步构建，构建时要能访问 PGDG

预构建镜像的 tag 形如 pg18、0.8.7-pg18、pg18-trixie，对应 PostgreSQL 18 和 pgvector 0.8.7。只做本地验证时，把下面的 compose 里 build 换成 image: pgvector/pgvector:0.8.7-pg18-trixie 就能跳过构建。

目录结构 ​

text
pgvector/
├── compose.yaml
├── .env
├── build/
│   └── Dockerfile
├── config/
│   └── postgresql.conf
├── init/
│   └── 01-vector.sql
├── secrets/
│   └── postgres_password.txt
└── data/

build/ 只放 Dockerfile，构建上下文里不能出现 data/ 或带密码的 compose 文件，否则这些内容会被发给构建器。

构建镜像 ​

build/Dockerfile：

dockerfile
ARG BASE_IMAGE
FROM ${BASE_IMAGE}

ARG PGVECTOR_DEB_VERSION

RUN set -eux; \
    test -n "$PGVECTOR_DEB_VERSION"; \
    postgres --version | grep -E '^postgres \(PostgreSQL\) 18\.6( |$)'; \
    apt-get update; \
    apt-get install -y --no-install-recommends "postgresql-18-pgvector=${PGVECTOR_DEB_VERSION}"; \
    grep -E "^default_version[[:space:]]*=[[:space:]]*'0\.8\.7'" "$(pg_config --sharedir)/extension/vector.control"; \
    rm -rf /var/lib/apt/lists/*

两处 grep 是刻意的版本护栏：基础镜像必须是 PostgreSQL 18.6，装上的扩展必须是 0.8.7。升级时基础镜像、包版本、两处 grep 里的版本号要一起改。漏改一处，构建会直接失败，而不是悄悄装错版本。

固定基础镜像和包版本 ​

先把 tag 解析成 digest：

bash
docker pull postgres:18.6-trixie
docker image inspect postgres:18.6-trixie --format '{{index .RepoDigests 0}}'

输出形如 postgres@sha256:...。多架构主机上，RepoDigests 给的是 manifest list 的摘要，直接填进 BASE_IMAGE 即可，构建时会按当前平台选子镜像；如果拿的是某个平台的子摘要，换架构构建会报平台不匹配。

把它填进 .env：

bash
# digest 用上一步 docker image inspect 的输出替换
BASE_IMAGE=postgres@sha256:...
PGVECTOR_DEB_VERSION=0.8.7-1.pgdg13+1

包版本不要猜。在基础镜像里查当前可用的版本：

bash
docker run --rm --entrypoint sh postgres:18.6-trixie -ec \
  'apt-get update && apt-cache madison postgresql-18-pgvector'

Debian 版本不同，包版本后缀也不同（trixie 是 pgdg13），以命令输出为准。PGDG 会下架历史包，构建成功后把镜像和包版本一起记录，别指望半年后还能用同一个版本号重新构建。

compose.yaml ​

yaml
name: pgvector

services:
  postgres:
    build:
      context: ./build
      args:
        BASE_IMAGE: ${BASE_IMAGE:?set in .env}
        PGVECTOR_DEB_VERSION: ${PGVECTOR_DEB_VERSION:?set in .env}
    image: local/postgres-vector:18.6-0.8.7
    pull_policy: never
    restart: unless-stopped
    shm_size: 1gb
    stop_grace_period: 60s
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD_FILE: /run/secrets/postgres_password
      TZ: Asia/Shanghai
    secrets:
      - postgres_password
    command:
      - postgres
      - -c
      - config_file=/etc/postgresql-custom/postgresql.conf
    volumes:
      - ./data:/var/lib/postgresql/data
      - ./config:/etc/postgresql-custom:ro
      - ./init:/docker-entrypoint-initdb.d:ro
    ports:
      - "127.0.0.1:5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "5"

secrets:
  postgres_password:
    file: ./secrets/postgres_password.txt

shm_size 不是可选项。并行建 HNSW 索引时，pgvector 会通过 /dev/shm 共享内存，容器默认只有 64MB，索引一大就会报 could not resize shared memory segment。设成 1gb 是给中等规模索引的起点，实际应不小于 maintenance_work_mem。

pull_policy: never 防止 Compose 去 Docker Hub 找 local/postgres-vector。镜像要先构建：

bash
docker compose build postgres
docker compose up -d

外部 postgresql.conf ​

官方镜像的配置在 PGDATA 里，直接改会被数据目录带着走，也不方便版本管理。把配置目录挂进容器、用 config_file 指过去，再把 PGDATA 里的原始配置 include 进来：

config/postgresql.conf：

conf
include '/var/lib/postgresql/data/postgresql.conf'

data_directory = '/var/lib/postgresql/data'
hba_file = '/var/lib/postgresql/data/pg_hba.conf'
ident_file = '/var/lib/postgresql/data/pg_ident.conf'

shared_buffers = 1GB
work_mem = 16MB
maintenance_work_mem = 256MB
max_parallel_maintenance_workers = 2

上面的内存参数只是起点，按容器内存和数据集调整，不要直接照抄。

include 是为了保留 initdb 生成的 locale、listen_addresses 等设置；data_directory、hba_file、ident_file 显式指回原位置，避免认证文件被当成配置目录的一部分。PGDATA 改过路径时，这三行也要跟着改。

配置是否被接受，不看容器有没有起来，看 pg_file_settings：

bash
docker compose exec postgres psql -U app -d app -c \
  "SELECT sourcefile, sourceline, name, setting, error FROM pg_file_settings WHERE error IS NOT NULL;"

错误为零行才说明语法和取值没问题。改完先 reload：

bash
docker compose exec postgres psql -U app -d app -c "SELECT pg_reload_conf();"

shared_buffers、max_connections 这类参数必须重启才生效。确认哪些参数还在等重启：

bash
docker compose exec postgres psql -U app -d app -c \
  "SELECT name, setting, source, pending_restart FROM pg_settings WHERE pending_restart;"

另外注意 ALTER SYSTEM 写的是 PGDATA 里的 postgresql.auto.conf，优先级高于外部配置文件。排查参数为什么没生效时，先看 pg_settings.source，不要直接怀疑挂载。

初始化与扩展 ​

init/01-vector.sql：

sql
CREATE EXTENSION IF NOT EXISTS vector;

这个目录只在 PGDATA 为空、容器第一次初始化时执行。已有数据目录时，脚本会被跳过，扩展要手工建：

bash
docker compose exec postgres psql -U app -d app -c \
  "CREATE EXTENSION IF NOT EXISTS vector;"

扩展是按数据库安装的，不是按实例。新建一个库就要再执行一次。CREATE EXTENSION 需要超级用户，POSTGRES_USER 创建出来的账号默认就是超级用户；换成业务账号执行会报权限错误。

向量表和索引 ​

先用三维向量确认语法：

sql
CREATE TABLE items (id bigserial PRIMARY KEY, embedding vector(3));

INSERT INTO items (embedding) VALUES ('[1,2,3]'), ('[4,5,6]');

SELECT id, embedding <=> '[3,1,2]' AS distance
FROM items
ORDER BY embedding <=> '[3,1,2]'
LIMIT 5;

实际表的结构大致是这样，维度换成自己模型的输出维度：

sql
CREATE TABLE documents (
    id bigserial PRIMARY KEY,
    tenant_id bigint NOT NULL,
    content text NOT NULL,
    embedding vector(1536) NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

HNSW 索引：

sql
SET maintenance_work_mem = '1GB';

CREATE INDEX documents_embedding_idx ON documents
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

查询时调大候选列表，召回率会更好，代价是变慢。下面的 $1、$2 是应用侧参数占位符，直接在 psql 里执行要换成字面量：

sql
SET hnsw.ef_search = 100;

SELECT id, content, embedding <=> $1 AS distance
FROM documents
WHERE tenant_id = $2
ORDER BY embedding <=> $1
LIMIT 10;

IVFFlat 建得更快、占内存更少，召回率通常不如 HNSW。它需要在有数据之后建，lists 的起点是 100 万行以内取 rows / 1000，超过 100 万行取 sqrt(rows)；查询时 probes 从 sqrt(lists) 起步。

sql
CREATE INDEX documents_embedding_ivf_idx ON documents
    USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);

SET ivfflat.probes = 10;

距离运算符要和索引的 operator class 对上：

运算符含义operator class
<->L2 距离vector_l2_ops
<#>负内积vector_ip_ops
<=>余弦距离vector_cosine_ops
<+>L1 距离vector_l1_ops

<#> 返回的是负内积，按它排序等价于按内积从大到小。用余弦距离时，写入前是否归一化不影响 <=> 的结果，但会影响和内积方案的换算。

维度上限容易踩：

类型可建索引的维度
vector2,000
halfvec4,000
bit64,000
sparsevec1,000 个非零元素

3072 维的模型输出可以存进 vector(3072)，但建不了 HNSW。要么降维，要么改用半精度（下面假设表里是 vector(3072)）：

sql
CREATE INDEX documents_embedding_half_idx ON documents
    USING hnsw ((embedding::halfvec(3072)) halfvec_cosine_ops);

查询也要做同样的转换：

sql
SELECT id FROM documents
ORDER BY embedding::halfvec(3072) <=> $1::halfvec(3072)
LIMIT 10;

验证 ​

bash
# 扩展版本
docker compose exec postgres psql -U app -d app -c \
  "SELECT extversion FROM pg_extension WHERE extname = 'vector';"

# 实际生效的配置文件
docker compose exec postgres psql -U app -d app -c "SHOW config_file;"

# 索引是否被使用
docker compose exec postgres psql -U app -d app -c \
  "EXPLAIN (COSTS OFF) SELECT id FROM documents ORDER BY embedding <=> (SELECT embedding FROM documents LIMIT 1) LIMIT 5;"

EXPLAIN 里出现 Index Scan using documents_embedding_idx 才说明走的是向量索引。小表或数据量太少时，规划器可能仍然选择顺序扫描，这种情况可以先用 SET enable_seqscan = off; 验证索引本身可用，再决定是否补数据或调参数。

备份与升级 ​

同一大版本内的补丁升级（18.6 → 下一个补丁版本）直接换镜像、保留 PGDATA 即可，不需要 pg_upgrade。即便如此也要先备份，并确认新镜像里的扩展包版本与数据目录兼容。

跨大版本（17 → 18）要走 pg_upgrade 或 dump/restore。新实例必须装好对应大版本的 pgvector 包，否则 pg_upgrade 会因为缺少扩展而失败。升级完成后：

sql
ALTER EXTENSION vector UPDATE;
REINDEX INDEX documents_embedding_idx;
ANALYZE documents;

ALTER EXTENSION 要在每个装了 vector 的数据库里执行。升级前读一遍 pgvector 的 changelog：0.8.2 到 0.8.7 之间修过 HNSW vacuum 和 IVFFlat 建索引的问题，从这些版本升上来时，重建索引比继续用旧索引稳妥。

备份用 pg_dump 或 pg_basebackup，不要在容器运行时直接复制 PGDATA。需要时间点恢复就开 WAL 归档，并把归档目录放在数据卷之外。

常见问题 ​

现象原因处理
extension "vector" is not available镜像里没装扩展，或包和 PG 大版本不匹配apt-cache madison postgresql-18-pgvector 确认包存在，重建镜像
type "vector" does not exist当前数据库没建扩展在该库执行 CREATE EXTENSION vector;
建索引报维度超限vector 超过 2,000 维降维，或改用 halfvec
建 HNSW 索引时报共享内存错误容器 /dev/shm 太小调大 shm_size，不低于 maintenance_work_mem
建索引很慢maintenance_work_mem 太小或并行度低提高内存和 max_parallel_maintenance_workers
初始化 SQL 没执行PGDATA 非空手工执行扩展和建表脚本
改了配置不生效config_file 没指向挂载文件，或 ALTER SYSTEM 覆盖查 SHOW config_file 和 pg_settings.source
容器启动后立刻退出数据目录权限与容器 UID 不匹配调整目录属主，不要直接 chmod 777
升级后查询报索引错误扩展或索引未重建执行 ALTER EXTENSION、REINDEX、ANALYZE

数据库端口只绑了 127.0.0.1。需要远程访问时走 SSH 隧道或带认证的反向代理，不要把 5432 直接开到公网。
