用 Docker Compose 部署 Keycloak 并接入 OIDC

Docker

用 Docker Compose 部署 Keycloak 26 并接入 OIDC，包含数据库、hostname 与反向代理配置、realm/client 创建和资源服务器校验

标签：
Docker Compose Keycloak OIDC 单点登录
发布于 2026年11月22日

前言 ​

Keycloak 提供 OIDC、OAuth 2.0、SAML 三种协议的统一登录，自带用户管理、角色、组、身份代理和登录页定制。对内部系统来说，它解决的是“每个系统一套账号”的问题：用户在一个地方登录，各业务系统只负责校验 token。

部署时有两处容易低估：一是 hostname，它决定 token 里的 iss，配错会让所有资源服务器拒绝 token；二是 issuer 的可达性，浏览器、业务容器、Keycloak 自己看到的地址可能不是同一个。

两种运行模式 ​

模式命令数据库HTTPS适用
开发模式start-dev默认内嵌 H2不要求本地试用、临时验证
生产模式start必须显式配置默认要求，前置代理时开 KC_HTTP_ENABLED正式环境

开发模式的内嵌数据库不适合任何需要保留数据的环境，重启即丢。正式环境从第一天就用 PostgreSQL。

目录结构 ​

text
sso/
├── compose.yaml
└── .env

.env：

bash
KEYCLOAK_DB_PASSWORD=CHANGEME-db
KEYCLOAK_ADMIN_PASSWORD=CHANGEME-admin

Keycloak 没有 KC_DB_PASSWORD_FILE 这类从文件读取数据库密码的机制，示例里用环境变量注入。.env 要限制权限，不要提交到仓库；生产环境也可以通过 vault 或启动脚本注入。

compose.yaml ​

yaml
name: sso

services:
  db:
    image: postgres:18-alpine
    restart: unless-stopped
    environment:
      POSTGRES_DB: keycloak
      POSTGRES_USER: keycloak
      POSTGRES_PASSWORD: ${KEYCLOAK_DB_PASSWORD:?set in .env}
    volumes:
      - keycloak-db:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U keycloak -d keycloak"]
      interval: 10s
      timeout: 5s
      retries: 5

  keycloak:
    image: quay.io/keycloak/keycloak:26.8.2
    restart: unless-stopped
    command: ["start"]
    depends_on:
      db:
        condition: service_healthy
    environment:
      KC_DB: postgres
      KC_DB_URL: jdbc:postgresql://db:5432/keycloak
      KC_DB_USERNAME: keycloak
      KC_DB_PASSWORD: ${KEYCLOAK_DB_PASSWORD:?set in .env}
      KC_BOOTSTRAP_ADMIN_USERNAME: admin
      KC_BOOTSTRAP_ADMIN_PASSWORD: ${KEYCLOAK_ADMIN_PASSWORD:?set in .env}
      KC_HOSTNAME: https://sso.example.com
      KC_HTTP_ENABLED: "true"
      KC_PROXY_HEADERS: xforwarded
      KC_HEALTH_ENABLED: "true"
      KC_METRICS_ENABLED: "true"
    ports:
      - "127.0.0.1:8080:8080"
      - "127.0.0.1:9000:9000"
    healthcheck:
      test:
        - CMD-SHELL
        - >-
          bash -c 'exec 3<>/dev/tcp/127.0.0.1/9000;
          printf "GET /health/ready HTTP/1.0\r\n\r\n" >&3;
          head -1 <&3 | grep -q "200"'
      interval: 30s
      timeout: 5s
      retries: 5
      start_period: 120s

volumes:
  keycloak-db:

说明：

  • KC_HOSTNAME 写完整的对外 URL。token 的 iss、发现文档里的地址、邮件里的链接都由它决定。
  • KC_HTTP_ENABLED=true 允许 8080 走明文，TLS 由前面的 Nginx/Caddy 终止；KC_PROXY_HEADERS=xforwarded 让 Keycloak 信任代理传来的 X-Forwarded-*，否则生成的跳转地址会退回 http://，登录后反复跳转。
  • 9000 是管理端口，提供 /health/ready、/health/live 和 /metrics。只绑定回环，不要通过反向代理暴露。
  • 镜像基于精简的 UBI，没有 curl。健康检查用 bash 的 /dev/tcp 直接发一个 HTTP 请求，这是镜像内可用的最小依赖。
  • KC_BOOTSTRAP_ADMIN_* 只在 master realm 还没有管理员时生效，之后修改环境变量不会重置已有密码。

TLS 由 Keycloak 自己承担时，去掉 KC_HTTP_ENABLED，把 8443 映射出来，并提供证书：

yaml
    environment:
      KC_HTTPS_CERTIFICATE_FILE: /certs/tls.crt
      KC_HTTPS_CERTIFICATE_KEY_FILE: /certs/tls.key
    volumes:
      - ./certs:/certs:ro
    ports:
      - "8443:8443"

已有 PostgreSQL 时，删掉 db 服务，把 KC_DB_URL 指向现有实例，并先建库：

sql
CREATE DATABASE keycloak;

表结构由 Keycloak 启动时自动创建，不要手工建表，也不要把建库脚本挂到已有实例的 docker-entrypoint-initdb.d（那只在数据目录为空时执行）。

反向代理 ​

以 Nginx 为例：

nginx
server {
    listen 443 ssl;
    server_name sso.example.com;

    ssl_certificate     /etc/nginx/certs/sso.crt;
    ssl_certificate_key /etc/nginx/certs/sso.key;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Port $server_port;
    }
}

X-Forwarded-Proto 和 X-Forwarded-Host 必须传，且 KC_PROXY_HEADERS 要与之匹配（Nginx 用 xforwarded，Traefik/Envoy 也可以发标准 Forwarded 头，对应 forwarded）。代理和 Keycloak 之间的 HTTP 只走回环或内网。Nginx 在宿主机上用 127.0.0.1:8080，在容器里改用服务名 keycloak:8080。

创建 realm 与 client ​

管理界面在 https://sso.example.com/admin/。手工点一遍不难，但环境重建时容易漏配置，建议用 kcadm.sh 脚本化（--server 也可以直接写对外地址）：

bash
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh config credentials \
  --server http://localhost:8080 \
  --realm master \
  --user admin \
  --password "$KEYCLOAK_ADMIN_PASSWORD"

docker compose exec keycloak /opt/keycloak/bin/kcadm.sh create realms \
  -s realm=demo -s enabled=true

docker compose exec keycloak /opt/keycloak/bin/kcadm.sh create clients -r demo \
  -s clientId=demo-api \
  -s enabled=true \
  -s publicClient=false \
  -s serviceAccountsEnabled=true \
  -s 'redirectUris=["https://app.example.com/*"]' \
  -s 'webOrigins=["https://app.example.com"]'

取客户端密钥：

bash
docker compose exec keycloak /opt/keycloak/bin/kcadm.sh get clients -r demo \
  -q clientId=demo-api --fields id,secret

概念对应关系：

Keycloak作用
realm租户边界，用户、client、角色都在 realm 内
client一个接入的应用；后端服务用 confidential + service account
redirectUris浏览器登录成功后允许跳回的地址，必须精确匹配
serviceAccountsEnabled允许用 client credentials 获取服务间调用的 token
audience资源服务器校验 token 是否发给自己的常见字段，默认不带，需要加 mapper

后端服务校验 token 时，除了签名和过期时间，通常还要检查 aud。Keycloak 默认生成的 access token 里 audience 往往只有 account 这类内置值，业务 API 需要在 client 上加一个 Audience mapper，把自己的标识写进 token。

验证 ​

发现文档里的 issuer 必须和预期完全一致：

bash
curl -fsS https://sso.example.com/realms/demo/.well-known/openid-configuration \
  | jq -r '.issuer, .jwks_uri'

预期 issuer 是 https://sso.example.com/realms/demo，不能多斜杠、不能是 http、不能是容器名。

用 client credentials 换 token：

bash
curl -s -X POST https://sso.example.com/realms/demo/protocol/openid-connect/token \
  -d grant_type=client_credentials \
  -d client_id=demo-api \
  -d client_secret="$DEMO_CLIENT_SECRET" \
  | jq -r '.access_token' \
  | cut -d. -f2 | base64 -d 2>/dev/null | jq .

payload 里的 iss 要和发现文档一致，exp 是过期时间（默认 5 分钟），azp 是发起请求的 client。

健康检查：

bash
curl -fsS http://localhost:9000/health/ready

接入 Spring Boot 资源服务器 ​

yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://sso.example.com/realms/demo

Spring 启动时会请求 issuer-uri + /.well-known/openid-configuration 拉取 JWKS，并校验 token 的 iss。这就要求应用容器也能访问这个公网地址。

常见的失败场景：

  • 应用在 Docker 网络里，sso.example.com 解析不到或没有出网，启动直接失败。
  • 应用能访问，但 DNS 指向了另一个实例，JWKS 和签发方不是同一套密钥。

解决方式按优先级：

  1. 让内网 DNS 把 sso.example.com 解析到反向代理，内外网使用同一个 issuer。这样应用侧不用改配置，也不用处理 issuer 不一致。
  2. 应用侧用 extra_hosts 把域名指到代理地址。
  3. 只配 jwk-set-uri 指向内网 Keycloak，但此时 Spring 默认不再校验 issuer，需要自己给 JwtDecoder 叠加 JwtValidators.createDefaultWithIssuer(...)，否则等于放弃了 issuer 校验。

如果业务确实要通过内网地址访问 Keycloak，可以打开后通道动态解析：

yaml
      KC_HOSTNAME: https://sso.example.com
      KC_HOSTNAME_BACKCHANNEL_DYNAMIC: "true"

它让 token endpoint 等后通道地址按请求的 Host 动态生成，但 KC_HOSTNAME 必须是完整 URL。不要在没搞清 issuer 的情况下直接关掉校验。

常见问题 ​

现象原因处理
启动报 HTTPS 相关错误生产模式默认要求 TLS配证书，或前置代理并设 KC_HTTP_ENABLED=true
登录后跳回 http:// 或反复跳转代理头没传或 KC_PROXY_HEADERS 不匹配补 X-Forwarded-Proto/Host，设置对应模式
502 Bad Gateway代理指向的端口不对，或 Keycloak 没起来看 docker compose logs keycloak，确认 8080 监听
token 被拒，提示 issuer 不匹配KC_HOSTNAME 与 discovery 的 issuer 不一致统一对外域名，检查 iss
改了 KC_BOOTSTRAP_ADMIN_PASSWORD 但密码没变管理员已存在，bootstrap 只执行一次用 kcadm.sh 重置密码
管理台空白或资源 404反向代理路径/主机头不对确认 Host 头和 KC_HOSTNAME
时间相关校验失败容器与客户端时钟偏差同步 NTP，容器挂载 /etc/localtime 不解决时钟
升级后无法回退启动时执行了数据库迁移升级前备份数据库，回退要恢复备份

版本上，26.8.2 是写这篇文章时的稳定版本。:latest 是可变标签，升级前先看 release notes 里的数据库迁移说明，并在测试环境跑一遍登录和 token 刷新。
