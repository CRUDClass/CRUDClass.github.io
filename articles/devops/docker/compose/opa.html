用 Docker Compose 部署 OPA 策略服务

Docker

用 Docker Compose 部署 OPA 策略服务，包含 Rego 策略与测试、bundle 分发、决策接口、应用接入与失败关闭

标签：
Docker Compose OPA Rego 策略即代码
发布于 2026年11月22日

前言 ​

把授权逻辑写进业务代码，通常会变成一堆散落在各个服务里的 if：角色判断、租户隔离、资源归属，每加一个接口就要改一次代码、发一次版。OPA（Open Policy Agent）把这些判断抽成独立的策略服务，业务代码只负责把“谁、对什么、做什么”打包成 JSON 问它一句。

OPA 本身是无状态的：策略（policy）和数据（data）从文件或 bundle 加载，输入（input）随每次请求传入，输出是一个决策（decision）。

text
业务服务 ──POST input──▶ OPA ──▶ {"result": true/false}
                          │
                          └── policies/ + data/（文件或 bundle）

它只做授权决策，不做认证。身份仍然由 Keycloak、JWT 或网关注入，OPA 只回答“这个身份能不能做这件事”。

目录结构 ​

text
policy/
├── compose.yaml
├── config/
│   └── opa-config.yaml
├── policies/
│   └── authz.rego
├── tests/
│   └── authz_test.rego
├── bundles/
│   └── authz.tar.gz
└── input.json

编写策略 ​

policies/authz.rego：

rego
package app.authz

import rego.v1

default allow := false

# 健康检查不需要授权
allow if {
	input.method == "GET"
	input.path == "/health"
}

# 管理员放行
allow if {
	"admin" in input.user.roles
}

# 普通用户只能读自己租户下的资源
allow if {
	input.method == "GET"
	"reader" in input.user.roles
	tenant := tenant_of_path(input.path)
	tenant == input.user.tenant
}

tenant_of_path(path) := tenant if {
	parts := split(path, "/")
	count(parts) >= 3
	tenant := parts[2]
}

Rego v1 有几处和旧写法不同：

  • default allow := false 必须有。没有默认值时，条件不满足的查询返回的是“未定义”，而不是 false，调用方很容易把空结果误判为拒绝或放行。
  • 多条 allow if 之间是逻辑或，任意一条成立即放行。
  • input.user.roles 不存在时，整条规则不成立，不会报错。这种“缺字段即拒绝”的行为适合授权场景。
  • Rego v1 要求规则体带 if，函数和集合用 contains。0.x 的 allow { ... } 写法在 1.x 会直接报语法错误。

测试策略 ​

策略也是代码，改动前先写测试：

tests/authz_test.rego：

rego
package app.authz_test

import rego.v1
import data.app.authz

test_admin_allowed if {
	authz.allow with input as {
		"method": "DELETE",
		"path": "/orders/1",
		"user": {"roles": ["admin"], "tenant": "acme"},
	}
}

test_reader_own_tenant_allowed if {
	authz.allow with input as {
		"method": "GET",
		"path": "/tenants/acme/orders",
		"user": {"roles": ["reader"], "tenant": "acme"},
	}
}

test_reader_other_tenant_denied if {
	not authz.allow with input as {
		"method": "GET",
		"path": "/tenants/other/orders",
		"user": {"roles": ["reader"], "tenant": "acme"},
	}
}

test_anonymous_denied if {
	not authz.allow with input as {
		"method": "GET",
		"path": "/orders/1",
		"user": {"roles": []},
	}
}

在本地跑，不用先起容器：

bash
docker run --rm -v "$PWD:/work" -w /work openpolicyagent/opa:1.22.4 \
  test -v policies tests

docker run --rm -v "$PWD:/work" -w /work openpolicyagent/opa:1.22.4 \
  check --strict policies tests

docker run --rm -v "$PWD:/work" -w /work openpolicyagent/opa:1.22.4 \
  fmt --diff policies tests

opa check --strict 会检查未使用的变量、命名冲突这类问题，比等到运行时才发现便宜得多。

compose.yaml ​

直接挂载策略目录，改动后重启容器即可加载：

yaml
name: policy

services:
  opa:
    image: openpolicyagent/opa:1.22.4
    restart: unless-stopped
    command:
      - run
      - --server
      - --addr=0.0.0.0:8181
      - --log-level=info
      - --log-format=json
      - /policies
    volumes:
      - ./policies:/policies:ro
    ports:
      - "127.0.0.1:8181:8181"
    read_only: true
    tmpfs:
      - /tmp
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    logging:
      driver: json-file
      options:
        max-size: "20m"
        max-file: "5"

--addr=0.0.0.0:8181 必须显式写。OPA 默认只监听 localhost，容器外访问不到。

策略文件以只读方式挂载，策略变更走“改文件、跑测试、重启”的流程，避免有人直接调 API 改线上策略。

决策接口 ​

查询走 /v1/data/<package path>/<rule>：

bash
curl -fsS http://localhost:8181/health

curl -s -X POST http://localhost:8181/v1/data/app/authz/allow \
  -H 'Content-Type: application/json' \
  -d '{"input":{"method":"GET","path":"/tenants/acme/orders","user":{"roles":["reader"],"tenant":"acme"}}}'

返回：

json
{"result": true}

规则未定义时返回 {}，没有 result 字段。调用方把没有 true 的响应都按拒绝处理，不用额外区分。

OPA 还提供：

接口用途
GET /health进程存活；带 ?bundles=true 时检查 bundle 是否加载成功
GET /metricsPrometheus 格式的运行指标
POST /v1/data/...带 input 查询决策
GET /v1/policies列出已加载策略
POST /v1/compile部分求值，适合一次性生成查询条件

bundle 分发 ​

策略文件多了以后，逐个挂载不现实。更常见的做法是 CI 构建 bundle，OPA 定期拉取：

bash
docker run --rm -v "$PWD:/work" -w /work openpolicyagent/opa:1.22.4 \
  build -b policies -o bundles/authz.tar.gz

config/opa-config.yaml：

yaml
default_decision: /app/authz/allow

bundles:
  authz:
    resource: /bundles/authz.tar.gz
    polling:
      min_delay_seconds: 10
      max_delay_seconds: 30

decision_logs:
  console: true

compose 里换成：

yaml
    command:
      - run
      - --server
      - --addr=0.0.0.0:8181
      - --config-file=/config/opa-config.yaml
    volumes:
      - ./config:/config:ro
      - ./bundles:/bundles:ro

此时不要再传 /policies，否则文件和 bundle 会同时加载，出现重复定义。

default_decision 让 GET / 直接返回 allow 的结果，健康检查类探针可以用它，不必构造完整 input。生产环境把 resource 换成对象存储或 HTTP 地址，并开启 bundle 签名校验，防止策略在传输过程中被替换。

接入业务 ​

一次授权调用的流程：

  1. 从已认证的身份里取出 subject、角色、租户，不要把原始 token 塞进 input。
  2. 组装 {method, path, user, ...}，POST 到 OPA。
  3. 只有返回 {"result": true} 才放行；超时、连接失败、非 200、缺字段一律拒绝。

Java 侧用 HttpClient 调用的骨架：

java
boolean allowed = policyClient.allow(Map.of(
    "method", request.getMethod(),
    "path", request.getRequestURI(),
    "user", Map.of(
        "id", user.id(),
        "roles", user.roles(),
        "tenant", user.tenant()
    )
));

接入时要注意：

  • 超时要短。授权在请求链路上，50~100ms 已经算长；OPA 一般是个位数毫秒，超时说明网络或 OPA 出了问题。
  • 失败关闭：拿不到决策就拒绝，不要 catch 之后默认放行。
  • 可以缓存，但要设短 TTL（例如 30 秒），并接受撤权延迟。按 subject + action + resource 做 key，不要缓存整个请求。
  • 不要把 OPA 当认证。它不知道密码、不签发 token，只根据传入的身份做判断。
  • 决策日志可能含敏感数据。decision_logs 会记录 input，生产环境要么关闭 console 输出，要么做脱敏和采样。

安全边界 ​

OPA 的 HTTP API 没有内置认证，而且提供写接口：

  • PUT /v1/policies/{id} 可以替换策略。
  • PUT /v1/data/{path} 可以改数据。

任何能访问 8181 的人都能改策略。所以要把访问面收窄：

  • 只绑定 127.0.0.1 或内网地址，不发布到公网。
  • 需要跨主机调用时，放在网关后面，由网关做认证和来源限制。
  • 生产环境用只读挂载的 bundle，配合签名校验，禁用在线改策略的流程。
  • 容器以非 root 运行，read_only + cap_drop: ALL，减少被利用后的影响面。

常见问题 ​

现象原因处理
启动报 rego_parse_error，提示 if 相关用了 0.x 的规则语法升级到 v1 写法，规则体加 if
查询返回 {} 而不是 false没有 default allow := false补默认值
容器外访问 8181 拒绝OPA 默认只监听 localhost加 --addr=0.0.0.0:8181
返回 404package 路径和 URL 不一致package app.authz 对应 /v1/data/app/authz/allow
bundle 不更新轮询间隔、文件路径或缓存问题检查 /health?bundles=true 和 OPA 日志
策略改了但没生效文件挂载后没有重载重启容器，或改用 bundle 轮询
OPA 内存持续上涨加载了过大的 data.json把大表放到外部数据源，或拆分 bundle
日志把磁盘写满decision_logs.console: true生产关闭 console，改为推送到日志系统并采样

策略改动建议先在本地跑 opa test，CI 里过 opa check --strict，再构建 bundle、灰度发布。OPA 的决策是同步返回的，一次错误的策略发布会影响所有接入方，测试和回滚预案比部署本身更重要。
