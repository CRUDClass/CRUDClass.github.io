示教-复现（四）：分级验证、现场踩坑与复盘

机器人 ROS2

让人敢按「去程」按钮的工程约束：V0–V4 分级验证、dry-run 的两个坑、发布者争抢、参数继承链与结构化日志，以及仍未解决的问题

标签：
现场验证 工程实践 复盘
发布于 2026年11月22日

前言 ​

前三篇是算法：免标定、收敛、降级。这一篇是把同一套代码放到真实场地上反复跑，决定它能不能被信任的，是验证顺序和日志。

一、分级验证，不许跳级 ​

级别内容车
V0页面 / 检测 / 视频流 / 示教 / 参数保存，控制话题发布者为 0不动
V1现场示教，生成设定点文件手推
V2架空干跑：运动原语方向与精度架空
V3推偏 20 cm，只跑伺服，看能否回原位短距
V4全程往返，量重复性全程

V3 最关键：它直接检验示教-复现这个假设成不成立，先 V3 再 V4，不要一上来跑 18 m。V2 也证明过价值：架空跑 90° 旋转时发现「转错方向也会达标」的判据缺陷，如果直接上车就是一次 10 倍超转。

二、dry-run 的两个坑 ​

坑一：没有透传。 顶层脚本带 --dry-run，但调用伺服子进程时没把参数传下去，结果干跑阶段伺服照样驱动车，这是安全漏洞，不是体验问题。

坑二：干跑仍走闭环。 更隐蔽：dry-run 时把发布器换成空对象是对的，但闭环退出条件依赖里程计变化。车不动、里程计不变，于是每步都空转到 deadline，干跑必卡死。

现在的规则写死两条：dry-run 沿调用链逐层透传；dry-run 路径跳过闭环等待，只打印意图。

python
def run_servo(target, dry):
    argv = [sys.executable, "servo.py", "--target", target]
    if dry:
        argv.append("--dry-run")       # 必须透传，否则干跑会真动车
    return subprocess.call(argv) == 0

三、实跑前必查 ​

残留的速度发布者会互相抢，抢不到的那个持续发零速，表现是车不动，很容易被误判成算法问题。每次实跑前跑两条命令：

bash
ps -ef | grep -E 'follower|route_http|fixed_route' | grep -v grep   # 应为空
ros2 topic info /cmd_vel                                            # Publisher 应为 0

清理进程时不要用宽泛的 pkill -f "ros2 launch"，会杀掉开机自启的驱动与底盘服务。匹配要精确到可执行文件路径。

四、参数只能有一条继承链 ​

所有参数来自一份集中式配置文件，由运维脚本 source 后逐层继承到示教页面 → 任务编排 → 伺服/巡线子进程。任何一环手动启动，整条链就静默回落到代码默认值：实测角速度上限变 0.08 而非 0.15、迭代上限变 60 而非 100，行为不对但没有一行报错。

识别方法只有一个：查进程的 environ，不要读代码猜。

同理，改动方向要分清：代码是「本机 → 底盘」，示教结果与日志是「底盘 → 本机」。方向搞反，就会出现「改了设定点但行为没变」。

五、限制与可调范围 ​

现场能改的和改不动的要分清，否则会把「参数没调对」和「物理上做不到」混在一起。

类别项说明
可现场调检测带行数、HSV 阈值、m00 门限系数、速度与增益、三轴容差改参数后重启服务生效，不必重示教
需要重示教标签尺寸、相机或分辨率更换、端点位置移动测量链变了，旧的 golden 作废
改不动的光照不足、红线镜面反射、横向里程计失真、惯性单元故障、底盘无横移只能换方案或改硬件，调参解决不了

底盘侧的限制也在最后一类。两轮差速没有横移能力，所以「转 90° + 走固定距离」的横移写法在里程计失真时不可用；纯轮式里程计横移时读数偏差 0.78x–5.97x；惯性单元 Z 轴失效让融合里程计不可用。这三条决定了横向只能靠标签连续反馈修正；长距离的中间段没有外部基准，要靠巡线或地面布点补上。

六、日志要能事后复算 ​

巡线每个控制周期写一行 CSV：

text
t, seq, mode, detected, erro_px, m00, odom_x, odom_y, odom_yaw,
yaw_ref, traveled, v, w, remaining

外加可选的定时整帧 jpg（保留最新两次）和一份 summary.json（退出码、耗时、检出率、各模式驻留时长、被门限拒帧计数）。

这些字段是复盘时的依据：中远场红区那次跑偏，是靠 m00 与 erro 的时序定位到红区侵入采样带；符号错误那次发散，是靠 dyaw 与 w 的符号对照确认越转越偏。没有这些数据，偶发跑偏只能靠猜。

七、结果与没解决的问题 ​

已达成的：

  • 短距方案（直行 + 原地掉头）去程/返程两轮验证通过，两端伺服收敛，终点 ±2 cm / ±1°；这是目前实际使用的方案；
  • 长距巡线只跑通过一次去程（18 m、检出 95%、终点伺服收敛），回程不稳定，方案暂停；
  • 掉头位姿改为示教相对角（实测 174.18° / 168.67°，而非名义 180°），跨重启有效，修掉固定 180° 带来的约 10° 几何偏差；
  • 单测覆盖控制律、状态机、污染门限、运动原语标定与真实污染帧回归。

还没解决的：

  • 回程巡线的红线镜面反射方向性。同一根红线，反方向行驶时饱和度下降（S 中位数 80 → 73，S ≥ 100 的像素 1792 → 597），丢线后容易追着右侧反光误检（偏差 +246 px）转几十度。这是物理问题，根治要换哑光胶带或补光；代码侧的「重捕获门槛提高」讨论过但没实施。
  • 横向里程计不可靠。纯轮式里程计在横移时读数失真 0.78x–5.97x，所以「转 90° + 走固定距离」这类横移原语被整体弃用，横向只能靠标签的连续反馈来修，这也限制了标签丢失时的兜底能力。
  • 惯性单元待修。修好后应把里程计源切回融合版本，旋转闭环会更稳。

八、可以搬走的五条 ​

  1. 有确定性系统误差的传感器，可以先考虑「同一个错犯两次」，再考虑标定。前提是测量链不变、示教与复现的相对位姿一致。
  2. 控制律里每个角度都要有明确分工：误差方位角决定前进方向，实测方位角决定转向，示教方位角定义平衡点。混用会同时得到饱和、震荡和稳态误差。
  3. 定步长容易过冲。按余差比例给预算、时长取先到者、每步只吃一半，收敛就单调了。
  4. 死区补偿要连续、要分场景。阶跃式抬升会把小误差放大成 bang-bang；在已经在动的弧行步里抬角速度，等于把控制器换成开关控制器。
  5. 降级路径要和主路径一样被测试。「丢线 2 s 后按里程计航向直行」这类支路必须能单独触发、单独验证。

系列 ​

  • （一）原理与测量：不标定相机也能做到 ±2cm 定点
  • （二）伺服：一条控制律同时收敛 x/z/yaw
  • （三）行驶：三融合状态机与丢线兜底
  • （四）验证：分级验证、现场踩坑与复盘
