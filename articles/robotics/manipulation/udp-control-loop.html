一、协议：一个包承载一整个身体 ​

与运动控制盒的通信是硬约定：一个 UDP 数据包同时携带双臂位姿、夹爪、腰部角度、头部和底盘。格式串只有一个：

python
PACK_FMT = "<cc3f3f3f7f1f3f3f7f1f1f3f1fiiff"
PACK_LEN = struct.calcsize(PACK_FMT)      # 162 字节
UDP_HEAD = 0xBB                           # 帧头
UDP_MODE_EPOS = 1                         # 位置控制模式

1.1 逐字段拆解 ​

< 表示小端、无对齐填充；c 是字符，f 是 4 字节浮点，i 是 4 字节整型。

字段类型个数字节含义
headc11固定 0xBB 帧头
modec111 = 位置控制
base_vel3f312底盘速度
left_translation3f312左臂 xyz（米）
left_orientation3f312左臂 rpy（度）
arm_q_exp_left7f728左臂关节角期望（本系统恒 0）
cap_leftf14左夹爪开合 [0, 1]
right_translation3f312右臂 xyz（米）
right_orientation3f312右臂 rpy（度）
arm_q_exp_right7f728右臂关节角期望（恒 0）
cap_rightf14右夹爪开合
waist_expf14腰部角度（度）
head_exp3f312头部三轴
flt_ratef14滤波系数，恒 1.0
switch_enable_disablei14使能脉冲
switch_start_stopi14启动脉冲
car_translationf14底盘平移
car_rotationf14底盘旋转

合计 2 + 38 × 4 + 2 × 4 = 162 字节。

1.2 完整打包函数 ​

python
def build_packet(pose, switch_enable_disable, switch_start_stop):
    base_vel = [0.0, 0.0, 0.0]
    arm_q_exp_left = [0.0] * 7
    arm_q_exp_right = [0.0] * 7
    head_exp = [0.0, 0.0, 0.0]
    flt_rate = 1.0
    car_translation = 0.0
    car_rotation = 0.0

    packet = struct.pack(
        PACK_FMT,
        bytes([UDP_HEAD]),
        bytes([UDP_MODE_EPOS]),
        *base_vel,
        *pose.left_translation,
        *pose.left_orientation_deg,
        *arm_q_exp_left,
        pose.cap_left,
        *pose.right_translation,
        *pose.right_orientation_deg,
        *arm_q_exp_right,
        pose.cap_right,
        pose.waist_exp,
        *head_exp,
        flt_rate,
        switch_enable_disable,
        switch_start_stop,
        car_translation,
        car_rotation,
    )
    if len(packet) != PACK_LEN:
        raise ValueError(f"Unexpected packet length: {len(packet)} != {PACK_LEN}")
    return packet

1.3 长度校验是唯一能抓字段错位的手段 ​

看最后那个 if len(packet) != PACK_LEN。它看起来是多余的，因为 struct.pack 参数个数不对时会直接抛异常。

但它防的是另一种情况：格式串本身写错，而参数个数恰好凑够。例如把某个 3f 写成 f、同时别处多写一个 f，总数不变，打包“成功”，但所有字段整体错位。控制盒收到的是一个完全错乱的位姿，机械臂会做出意料之外的动作，而软件侧一切正常。

长度校验是唯一能在发送前抓住这类错误的手段，所有二进制协议打包都该有这一行。

1.4 未激活通道填什么 ​

包里两条臂都在，但通常只动一条。字段恒为 0 的有：底盘速度、关节角期望、头部、底盘平移/旋转。这些是“本系统不使用”的通道，填 0 是安全的。

但未激活的那条臂不能填 0：填 0 意味着“请把臂移到原点”，那是机架内部。见第三节。

二、单位边界：只在两处转换 ​

状态回读的字段编码与控制包不同：

状态回读控制包
位置前三位mmm
姿态后三位raddeg
夹爪归一化 [0,1]归一化 [0,1]

转换集中在一个函数里：

python
def rad_to_deg(values):
    return [float(math.degrees(v)) for v in values]


def clamp01(value):
    return max(0.0, min(1.0, float(value)))


def pose_from_system_info(msg):
    left_translation  = [float(msg.arm_pose_left[i])  / 1000.0 for i in range(3)]
    right_translation = [float(msg.arm_pose_right[i]) / 1000.0 for i in range(3)]
    left_orientation_deg  = rad_to_deg([float(msg.arm_pose_left[i])  for i in range(3, 6)])
    right_orientation_deg = rad_to_deg([float(msg.arm_pose_right[i]) for i in range(3, 6)])

    cap_left = 1.0
    cap_right = 1.0
    try:
        if len(msg.gripper.cur_pose) >= 2:
            cap_left  = clamp01(msg.gripper.cur_pose[0])
            cap_right = clamp01(msg.gripper.cur_pose[1])
    except Exception:
        pass                                  # 夹爪字段缺失时用默认值，不阻断运动

    waist_exp = 0.0
    try:
        if len(msg.waist_exp) >= 1:
            waist_exp = float(msg.waist_exp[0])
    except Exception:
        pass

    return ArmPose(
        left_translation=left_translation,
        right_translation=right_translation,
        left_orientation_deg=left_orientation_deg,
        right_orientation_deg=right_orientation_deg,
        cap_left=cap_left,
        cap_right=cap_right,
        waist_exp=waist_exp,
    )

系统内部一律用米和度，只在两个边界上转换：读状态时转进来，写日志时转出去。

混用单位是这类系统最经典的 bug 来源。它的特征很好认：

现象大概率原因
误差是整数倍（1000×）mm/m 混用
误差是 57.3× 或 0.017×rad/deg 混用
姿态突然翻转到奇怪角度度当成弧度（360° 被当成 6.28 rad）

看到“差了一千倍”先查单位，不要查算法，这一条能省下大量时间。

2.1 两个 try/except 的取舍 ​

夹爪与腰部字段用 try 包住，缺失时用默认值。这是个有意的设计选择：

  • 夹爪默认 1.0（保持闭合姿态）：状态回读里没有这个字段，不该让整个运动失败；
  • 腰部默认 0.0（不转），即中立位。

运动控制的主链路不该因为一个可选字段的缺失而中断，但要明确哪些字段是“可选”（默认值有物理意义），哪些是“必需”（缺失必须报错）。位置和姿态属于后者：缺失就该拒绝运动，用 0 代替会撞机架。

三、未激活臂：为什么必须填常量 ​

这是整套控制里最反直觉、也最容易出错的一条。

包里两条臂都在，但通常只动一条。另一条填什么？答案是填一个固定的中立位常量：

python
NEUTRAL_LEFT_XYZ_M = [0.51, -0.20, 0.225]
NEUTRAL_LEFT_RPY_DEG = [-0.00042, -0.00032, 0.00552]
NEUTRAL_RIGHT_XYZ_M = [0.51, -0.20, 0.225]
NEUTRAL_RIGHT_RPY_DEG = [0.00042, -0.00032, -0.00510]

这组数字对应的就是待机位：末端停在离基准半米出头、高 22.5 cm 处，两条臂都在这附近。而这里不能填「从状态回读拿到的实时位姿」，原因值得说清。

控制盒把收到的位姿当作绝对目标，以 60 Hz 持续驱动。如果把测量位姿喂回去，就形成了闭环：

目标 = 测量值  ->  控制盒驱动  ->  实际移动  ->  新的测量值  ->  目标更新  ->  ...

这个回路穿过了三个引入延迟与量化的环节：

环节引入的问题
状态回读的 UDP 广播延迟（毫秒级）+ 丢包（可能整帧丢失）
控制盒内部滤波（flt_rate）相位滞后
伺服位置环响应延迟 + 超调

控制论的结论很直接：相位滞后加上增益过大就是振荡。

现场表现是那条“不动”的臂持续微微抖动。操作员会以为是机械问题或驱动器参数问题，而真正原因是软件把测量值喂回了目标。

填常量则完全切断回路：未激活的臂收到一个恒定的目标，控制盒把它保持住即可。抖动消失。

同理，激活臂的初始位姿也要用中立位常量，不用实时读数。只有在「使能 + 启动」脉冲完成之后，才开始用 command_pose 跟踪目标，代码里那个 neutral_pose() 就是为这个存在的。

3.1 一个可迁移的判据 ​

任何“测量值 → 目标值”的直接回灌，都要先算一遍相位裕度。如果通道里有任何延迟或量化，回灌就是在给系统加一个延时环节。

这条不只适用于机械臂。温度控制里把实测温度当设定值、队列管理器里把积压量当目标速率、视频码率控制里把实测码率当目标码率，都是同一类错误。

四、唯一发送线程 ​

python
class PoseSender:
    def __init__(self, sock, udp_ip, udp_port, hz, pose):
        self.sock = sock
        self.udp_targets = normalize_udp_targets(udp_ip)
        self.udp_port = udp_port
        self.interval = 1.0 / hz
        self.pose = pose
        self.lock = threading.Lock()
        self.stop_event = threading.Event()
        self.thread = None
        self.sent_count = 0
        self.last_error = None

    def start(self):
        if self.thread is not None:
            return
        self.thread = threading.Thread(target=self._run, daemon=True)
        self.thread.start()

    def update_pose(self, pose):
        with self.lock:
            self.pose = pose

    def stop(self):
        self.stop_event.set()
        if self.thread is not None:
            self.thread.join(timeout=1.0)

    def _run(self):
        while not self.stop_event.is_set():
            with self.lock:
                packet = build_packet(self.pose, 0, 0)
            for target in self.udp_targets:
                try:
                    self.sock.sendto(packet, (target, self.udp_port))
                    self.sent_count += 1
                    self.last_error = None
                except OSError as exc:
                    self.last_error = f"{target}:{self.udp_port} {exc}"
            time.sleep(self.interval)          # 1/60 s

调用方只做一件事：调 update_pose(pose) 改状态，自己不负责发包。

4.1 这条规则被违反时的症状 ​

如果另有一个线程也在发包（比如“运动阶段”直接调用了 send_phase），两个发送者会交替发出不同的目标位姿。控制盒收到的是一串 30 Hz 的 A、30 Hz 的 B 交替序列。

机械臂的表现就是在两个位置之间来回走。

现场描述通常是「机械臂在前伸和回退之间振荡」。这个症状很有误导性：看起来像控制参数（增益过大、滤波太弱）的问题，实际根本原因是有两个发送者。

判据是振荡的周期约等于两倍发送间隔，而不是伺服系统的自然频率：两个发送者时，周期正好是两倍帧间隔；增益问题时，周期由机械动力学决定。

4.2 串行化的正确做法 ​

代码用一把可重入锁把整个运动序列串起来：

python
def move_to_xyz(self, xyz):
    with self.control_lock:                 # threading.RLock
        return self._move_to_xyz_locked(xyz, smooth=False)

所有 UDP 操作、所有全局状态修改（arm_side、transform、tool_offset、waiting_position）都在这把锁内。禁止并发。

用 RLock 而不是 Lock 的理由是：内部方法之间会互相调用（比如 return_to_waiting_position 内部调 set_active_arm），用普通锁会自我死锁。

4.3 发送频率与「到达率」 ​

60 Hz 意味着每 16.7 ms 一个包。控制盒按到达节奏工作，实际到达率比标称频率更要紧。

三个会让到达率下降的因素：

  • 广播到多个目标地址时，逐个 sendto，总耗时随目标数线性增长；
  • 发送线程被 GIL 抢占（同进程里有图像处理、YOLO 子进程通信）；
  • time.sleep(interval) 不精确（实际睡眠通常比请求长 1–2 ms）。

所以 _run 里用 time.sleep(self.interval) 而没有做“补偿式调度”（记录上次发送时间、动态调整睡眠）。如果要做严格频率，应该改成：

python
next_t = time.monotonic()
while not stop:
    send...
    next_t += self.interval
    sleep(max(0.0, next_t - time.monotonic()))

代价是复杂度上升（要处理积压、跳帧）。在这个系统里，控制盒对频率的容忍度足够，简单实现更可靠。够用的简单优于精确的复杂，前提是你知道容忍度有多大。

五、Prepare 时序：帧数即时间 ​

使能、启动、保持，每一步都发固定帧数：

python
def prepare(self, sync_feedback=False, feedback_timeout_sec=0.0):
    with self.control_lock:
        self.last_action = "prepare started"
        self.last_error = None

        if self.sender is not None:
            self.sender.stop()
            self.sender = None
        if sync_feedback:
            synced = self.sync_command_translation_from_feedback(feedback_timeout_sec)
            if not synced:
                self.last_action = "prepare started without feedback sync"

        pose = copy_pose(self.command_pose)
        send_phase(self.sock, self.udp_targets, cfg.UDP_PORT, cfg.CONTROL_HZ,
                   cfg.HOLD_FRAMES, pose, label="hold current pose")
        send_phase(self.sock, self.udp_targets, cfg.UDP_PORT, cfg.CONTROL_HZ,
                   cfg.PULSE_FRAMES, pose, switch_enable_disable=1, label="enable pulse")
        send_phase(self.sock, self.udp_targets, cfg.UDP_PORT, cfg.CONTROL_HZ,
                   cfg.SETTLE_FRAMES, pose, label="settle after enable")
        send_phase(self.sock, self.udp_targets, cfg.UDP_PORT, cfg.CONTROL_HZ,
                   cfg.PULSE_FRAMES, pose, switch_start_stop=1, label="start pulse")
        send_phase(self.sock, self.udp_targets, cfg.UDP_PORT, cfg.CONTROL_HZ,
                   cfg.SETTLE_FRAMES, pose, label="settle after start")

        self.prepared = True
        self.hold_pose(pose)                        # 交给 60 Hz hold 线程维持
        self.last_action = "prepare completed"
        self.last_prepare_time = time.time()

60 Hz 下换算：

阶段帧数时长作用
hold current pose601.0 s告诉控制盒“我在这里”，建立基线
enable pulse100.17 s使能脉冲
settle after enable1803.0 s等使能稳定
start pulse100.17 s启动脉冲
settle after start1803.0 s等启动稳定

5.1 为什么用帧数而不是秒 ​

因为帧数正是控制盒的语义单位：它按包的到达节奏工作，而不是按墙钟。

如果用秒定义时序，那么把频率从 60 改成 30 时，物理时序全变（“等 3 秒”变成了“等 90 帧”）。用帧数定义，改频率时控制盒看到的行为序列完全一致，只是墙钟时间翻倍。

这是一个不太显眼的正确性保证：时序参数该用被控对象的语言，而不是人的语言。

5.2 脉冲为什么发 10 帧 ​

python
def send_phase(sock, udp_ip, udp_port, hz, frames, pose,
               switch_enable_disable=0, switch_start_stop=0, label=""):
    targets = normalize_udp_targets(udp_ip)
    interval = 1.0 / hz
    packet = build_packet(pose, switch_enable_disable, switch_start_stop)
    for _ in range(frames):
        for target in targets:
            try:
                sock.sendto(packet, (target, udp_port))
            except OSError as exc:
                print(f"[udp] failed to send to {target}:{udp_port}: {exc}")
        time.sleep(interval)

注意整个 phase 只构造一次 packet，循环里反复 sendto。这既省 CPU，也保证同一 phase 内所有帧内容严格一致：如果每帧重新构造，位姿对象可能被别处改掉，相位内就出现了变化的位姿。

switch_enable_disable = 1 发 10 帧，就是 10 次脉冲，而不是发一帧值为 1、再发一帧值为 0。

原因在于控制盒只认到达的脉冲，不认保持的位。而 UDP 会丢包，发 10 次能把“至少到达一次”的概率提到很高。如果只发 1 帧，丢包率 10% 就意味着 10% 的启动失败，而且失败是静默的。

六、分段移动：路径上有什么，没人知道 ​

一次大位移如果直接下目标，机械臂会全速冲过去。这段路径上有什么，软件不知道。所以慢速分段：

python
def move_to_xyz_locked(self, xyz, smooth=False, step_m=None, step_interval_sec=None,
                       stop_event=None, approach_axis=None, retreat=False):
    if not self.prepared:
        self.prepare()

    current = copy_pose(self.command_pose)
    start  = np.array(arm_translation(current, self.arm_side), dtype=np.float64)
    target = np.array([float(v) for v in xyz], dtype=np.float64)
    delta  = target - start
    delta_norm = float(np.linalg.norm(delta))

    # 安全闸门：单次位移过大直接拒绝
    if delta_norm > cfg.MAX_DELTA_M:
        raise RuntimeError(f"Target move too large: {delta_norm:.3f}m > {cfg.MAX_DELTA_M:.3f}m")

    if not smooth:                       # fast 模式：一次到位
        pose = self.build_pose([float(v) for v in xyz])
        self.hold_pose(pose)
        return {"target_xyz": xyz, "delta_m": delta.tolist(),
                "delta_norm_m": delta_norm, "hold_only": True, "smooth": False}

    step = max(0.0005, float(cfg.INSPECTION_SLOW_MOVE_STEP_M))              # 3 mm
    interval = max(0.0, float(cfg.INSPECTION_SLOW_MOVE_STEP_INTERVAL_SEC))  # 80 ms

    # 两相位拆分：把 delta 分解成"进给轴分量"与"其余分量"
    axis_map = {"x": 0, "y": 1, "z": 2}
    if approach_axis and approach_axis in axis_map:
        axis_idx = axis_map[approach_axis]
        feed = np.array([0.0 if i != axis_idx else delta[i] for i in range(3)])
        lateral = np.array([delta[i] if i != axis_idx else 0.0 for i in range(3)])
        # 接近：先横移再进给；撤离：先退出再横移
        phase_specs = ([("approach_axis", feed), ("lateral", lateral)] if retreat
                       else [("lateral", lateral), ("approach_axis", feed)])
    else:
        phase_specs = [("linear", delta)]

    self.reset_tau_monitor()
    collision = None
    total_steps = 0
    phase_start = start.copy()

    for label, phase_delta in phase_specs:
        if collision is not None:
            break
        phase_norm = float(np.linalg.norm(phase_delta))
        if phase_norm < 1e-9:
            continue
        phase_steps = max(1, int(np.ceil(phase_norm / step)))

        for step_index in range(1, phase_steps + 1):
            if stop_event is not None and stop_event.is_set():
                break
            if collision is not None:
                break

            alpha = step_index / phase_steps
            interp_xyz = (phase_start + phase_delta * alpha).tolist()
            self.hold_pose(self.build_pose([float(v) for v in interp_xyz]))

            if interval > 0.0 and step_index < phase_steps:
                if stop_event is not None:
                    if stop_event.wait(interval):        # 可中断的 sleep
                        break
                else:
                    time.sleep(interval)

            if not retreat and cfg.COLLISION_DETECT_ENABLED:
                collision = self.check_collision(step_index, step_index == 1)

        phase_start = phase_start + phase_delta
        total_steps += phase_steps

    return {"target_xyz": xyz, "smooth": True, "steps": total_steps,
            "step_m": step, "step_interval_sec": interval,
            "approach_axis": approach_axis, "retreat": retreat, "collision": collision}

6.1 速度与检测分辨率 ​

3 mm / 80 ms 约等于 37.5 mm/s，比全速慢一个数量级。

每步之间采一次力矩，所以碰撞检测的空间分辨率就是 3 mm：机械臂最多前进 3 mm 就会被发现异常。这个数字不是随便选的：

  • 太大（比如 10 mm）：碰撞时来不及停，冲击能量大；
  • 太小（比如 0.5 mm）：路径耗时涨 6 倍，且 UDP 帧率撑不住。

3 mm 在“停得住”和“跑得完”之间。

6.2 两相位接近：顺序决定安全 ​

以进给轴为 X 为例：

场景相位顺序理由
接近目标lateral（Y/Z 对齐）→ approach（X 进给）先对准再进给
撤离目标approach（X 后退）→ lateral（Y/Z 横移）先退出再横移

如果直接走斜线，末端会沿着一条对角线扫过去，路径上擦到旁边物体的概率大增。

这个规则和“倒车入库”的直觉一样：先停到正确的高度再往前顶；倒出来的时候先退，再打方向。

代码里判断的是 if retreat，而不是根据“目标离原点远近”，由调用方声明意图比由算法猜测更可靠。回待机位时显式传 retreat=True。

6.3 安全闸门 ​

python
if delta_norm > cfg.MAX_DELTA_M:
    raise RuntimeError(f"Target move too large: {delta_norm:.3f}m > {cfg.MAX_DELTA_M:.3f}m")

单次位移上限 1.0 m，超限直接抛异常而不是钳制到上限。

为什么抛异常而不是钳制？超限意味着上游出了问题（标定错了、深度飞点、坐标乱套）。静默钳制会让机械臂“动了一点但没到位”，操作员以为成功了，然后在一个错误的位置拍照。异常能让人立刻知道出事，钳制只会把错误推后。

6.4 可中断性 ​

python
if stop_event is not None:
    if stop_event.wait(interval):     # 阻塞直到超时或被 set
        break
else:
    time.sleep(interval)

stop_event.wait(interval) 与 time.sleep(interval) 的差别：

time.sleepEvent.wait
能被中断不能能（set() 立即唤醒）
急停响应等本次 sleep 结束（最长 80 ms）立即

80 ms 的差别看起来很小，但在分段移动里，急停的响应延迟决定了机械臂还会多走多远：80 ms × 37.5 mm/s = 3 mm，正好是一个步长。

所有长循环里的 sleep 都该用可中断的原语。这不是优化，是让「停止」这个操作在语义上真的成立。

七、把整条回路的时序串起来 ​

一次巡检里，控制回路的时序大致是：

prepare:   1.0 s hold  ->  enable  ->  3.0 s settle  ->  start  ->  3.0 s settle
每点:      ~3 mm 步进 × N 步（每步 80 ms）  +  10 s 稳定
回位:      同样分段  +  3 s 稳定

时间预算的大头是等待，不是运动。第一篇那个“宁可多等几秒”的取舍就落在这里：每次等待都在消除一个不确定性来源：

等待消除的不确定性
1.0 s hold状态回读的滞后（先让控制盒和真实位姿同步）
3.0 s settle（×2）使能/启动状态机的迁移时间
每点 10 s机械余振 + 相机自动曝光收敛
切臂 3 s换外参后的位姿稳定
红灯 5 s 复查指示灯闪烁的相位

八、小结 ​

控制回路这一篇的七条：

  1. 162 字节定乾坤，一个包承载整个身体，长度校验是唯一能抓字段错位的手段；
  2. 单位只在边界转一次，误差是整数倍时先查单位；
  3. 未激活的通道必须填常量，把测量值回灌成目标等于给系统加一个延时环节，结果是振荡；
  4. 只能有一个发送线程，两个发送者的症状是「前伸-回退振荡」，周期约为两倍帧间隔；
  5. 时序用帧数定义，因为那是控制盒的语言，改频率时行为序列不变；
  6. 脉冲要重复发，控制盒认到达不认保持，UDP 会丢包；
  7. 分段移动的两相位顺序决定安全，接近时先横移后进给，撤离时先进给后横移，且 sleep 必须可中断。

系列结语 ​

五篇下来，这套系统没有用到任何前沿算法：没有学习型控制，没有端到端视觉伺服，也没有最优轨迹规划。它用的全是经典工具：一次 PnP、一次 SVD、一次最小二乘、一次 connected components、一次按距离的贪心匹配。

它难的地方在别处：

  • 每一环的边界条件（两种深度编码、反射修正、预处理一致性、单位转换）；
  • 每个不确定性的量化（深度散度、重投影 RMSE、剔除率、rank、力矩基线）；
  • 每个失败路径的兜底（降级留痕、finally 回位、硬超时、双判据碰撞检测）。

如果只记一条：系统的可靠性不取决于算法有多先进，而取决于你对每一个边界条件和失败路径处理得有多细。
