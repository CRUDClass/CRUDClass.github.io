一、部署才是难点 ​

训练一个 YOLO 模型是今天的标准流程：标注几百张图、跑几轮训练、看 mAP 曲线。真正的工程量在把它放到目标机器上：一台没有 GPU、Python 环境受限、算子支持不全的 ARM 板。

实际遇到的五类问题，按踩坑概率排序：

问题表现后果
后端不可用onnxruntime 装不上 / 算子不支持起不来，或静默用慢路径
预处理不一致训练用 letterbox，推理用 resize框系统偏小，不报错
输出布局不匹配4+C 与 5+C 布局混用框全挤在左上角
长宽比畸变输入 736 而相机 720形状被拉伸 2.2%
类别语义混淆「红色物体」判成「红灯」误报，且很难复现

二、三后端与自动回退 ​

模型在训练机上导出 ONNX，推理端支持三种后端：

python
def detect_yolo_points(image_path, model_path, ...):
    suffix = os.path.splitext(model_path)[1].lower()
    if suffix == ".onnx":
        common_args = (image_path, model_path, confidence, iou,
                       class_names, input_width, input_height, preprocess_mode)

        if backend == "onnxruntime":
            if not _ORT_AVAILABLE:
                raise RuntimeError(
                    "YOLO_ONNX_BACKEND='onnxruntime' but onnxruntime is not installed.")
            return detect_onnx_ort(*common_args)

        if backend == "opencv_dnn":
            return detect_onnx(*common_args)

        if _ORT_AVAILABLE:                          # backend == "auto"
            try:
                return detect_onnx_ort(*common_args)
            except Exception as exc:
                print(f"[yolo] onnxruntime failed, falling back to cv2.dnn: {exc}",
                      file=sys.stderr)
        return detect_onnx(*common_args)

    if suffix == ".pt":
        return detect_pt(image_path, model_path, ...)   # 训练机回退路径
    raise ValueError(f"Unsupported YOLO model format: {model_path}")

2.1 为什么默认 auto ​

两个后端各自覆盖对方的短板：

后端优点短板
onnxruntime算子覆盖全，支持较新的检测头（含 TopK 等）ARM 上安装困难，需匹配 ABI
cv2.dnn随 OpenCV 自带，零安装成本算子集受限，新架构可能加载失败

较新的检测头采用 one2one 匹配（免 NMS 直出），其中包含 TopK、Gather 等算子，OpenCV DNN 不一定支持。而某些 ARM 板子上 ORT 就是装不上。

所以默认 auto：先试能力强的，失败退回一定能跑的。这不是性能优化，是可用性策略：宁可跑得慢一点，也不要起不来。

2.2 回退时必须留日志 ​

python
print(f"[yolo] onnxruntime failed, falling back to cv2.dnn: {exc}", file=sys.stderr)

这一行让「为什么变慢了」有答案。没有它，现场表现是“检测耗时从 80 ms 涨到 300 ms，但功能正常”，排查方向会跑到模型大小、图像分辨率、CPU 占用上去，而真正原因是后端静默降级了。

所有降级路径都该留痕，这是部署代码和实验代码的区别之一。

三、预处理一致性：最容易出的系统性错误 ​

3.1 两种模式 ​

python
def preprocess_image(image, input_width, input_height, mode):
    height, width = image.shape[:2]

    if mode == "resize":
        resized = cv2.resize(image, (input_width, input_height),
                             interpolation=cv2.INTER_LINEAR)
        return resized, input_width / width, input_height / height, 0.0, 0.0, "resize"

    # letterbox：等比缩放到画布内，空白填 114
    scale = min(input_width / width, input_height / height)
    new_width  = int(round(width  * scale))
    new_height = int(round(height * scale))
    resized = cv2.resize(image, (new_width, new_height),
                         interpolation=cv2.INTER_LINEAR)

    canvas = np.full((input_height, input_width, 3), 114, dtype=np.uint8)
    pad_x = (input_width  - new_width)  / 2.0
    pad_y = (input_height - new_height) / 2.0
    left = int(round(pad_x - 0.1))
    top  = int(round(pad_y - 0.1))
    canvas[top:top + new_height, left:left + new_width] = resized

    return canvas, scale, scale, float(left), float(top), "letterbox"

两种模式返回同一组五个值：

(processed_image, scale_x, scale_y, pad_x, pad_y, mode_name)

这五个值必须一路传到解码阶段，因为模型输出的框是相对于输入图像的，要还原到原图才能用。

3.3 -0.1 不是笔误 ​

python
left = int(round(pad_x - 0.1))
top  = int(round(pad_y - 0.1))

这是 Ultralytics letterbox 实现的舍入约定。他们用 round(x - 0.1) 而不是 round(x)，为了在 .5 边界上偏向内侧（Python 的 round 是 banker's rounding，行为与 C 的 round 不同）。

如果自己写 letterbox 而不跟着这个约定，在特定分辨率下会差 1 像素。1 像素看起来无所谓，但训练时的标签也是按同样约定算的，推理侧差 1 像素等于把整个坐标系平移了 1 像素，对框中心的精度有直接影响。

3.4 训练-推理必须逐字一致 ​

这是最容易翻车、也最难发现的一条：

训练用 letterbox  ->  推理用 resize
  -> 长边方向框系统偏小约 (1 - s) 的比例
  -> 抓取位置持续偏移
  -> 不报错、不崩溃、只是"不太准"

这种误差不会报错，只会让抓取位置慢慢偏掉，而人会怀疑标定、怀疑深度、怀疑机械臂，就是不会怀疑预处理。

所以「预处理模式」必须是一个显式配置项，训练脚本和推理脚本读同一个值：

python
YOLO_INPUT_WIDTH  = 1280
YOLO_INPUT_HEIGHT = 736
YOLO_PREPROCESS_MODE = "resize"      # 必须与训练一致

反向验证的方法：拿一张训练图，用推理端的预处理跑一遍，再用训练端的预处理跑一遍，逐像素比较，差值全为 0 才算一致。

四、输出布局自适应 ​

4.1 三种布局 ​

不同代的检测头输出 shape 不同：

布局每行长度置信度来源框格式代表
A4 + Cclass score 直接是置信度cx, cy, w, hv8 / v11 / v26
B5 + Cobjectness × class scorecx, cy, w, hv5 / v7
C6第 5 列x1, y1, x2, y2已做 NMS 的导出

4.2 用通道数反推 ​

python
def normalize_output(output, class_count=0):
    pred = np.squeeze(np.asarray(output))
    if pred.ndim != 2:
        raise ValueError(f"Unexpected YOLO ONNX output shape: {output.shape}")

    if class_count > 0:
        raw_ch = {4 + class_count, 5 + class_count}
        if pred.shape[0] in raw_ch and pred.shape[0] < pred.shape[1]:
            pred = pred.T                          # (4+C, N) -> (N, 4+C)
        elif pred.shape[0] == 6 and pred.shape[1] > 6:
            pred = pred.T                          # 已 NMS 的 6 列
    elif pred.shape[0] < pred.shape[1] and pred.shape[0] <= 128:
        pred = pred.T
    return pred

思路是用通道数反推布局。若第一维等于 4+C 或 5+C 且小于第二维，说明是「通道在前」的布局，转置成「每行一个框」。

判断条件里有两个细节：

  • pred.shape[0] < pred.shape[1] —— 只有当行数少于列数时才是「通道在前」。如果一张图只检出 3 个框，网络输出可能是 (4+C, 3)，此时行数大于列数，转置判断就要反过来。用数量关系判断布局是有边界的，代码用 < 保守处理，极端情况下会漏转置，但这在实际中几乎不出现，因为输出通常是固定网格（如 8400 行）。
  • <= 128 —— 没有类别数信息时（分支 2），用「通道数 ≤ 128」作为合理性上限，防止把 (8400, 4) 误当成通道在前。

这段代码本质上是启发式，不保证对所有模型正确。可靠性来自两点：类别数已知（class_count > 0 走分支 1），以及导出后立即用一张图验证一次。

4.4 归一化还是像素 ​

有一个必须明确的问题：框坐标是归一化到 [0, 1]，还是输入尺寸下的像素？

代码里按像素处理（x - w / 2），说明导出时没有开归一化输出。

判断方法：如果模型输出的是归一化坐标，而按像素处理，所有框会挤在图像左上角的几个像素内，症状非常显眼，一眼就能定位。反过来，像素当归一化会导致框大到覆盖整张图。

这个错误虽然显眼，但只有在拿到第一张推理结果时才会暴露。所以部署流程的第一步永远是「跑一张已知图，肉眼看框的位置对不对」，而不是「先跑一整轮巡检」。

这里的 np.array(keep).reshape(-1) 是跨 OpenCV 版本兼容的写法：OpenCV 4.x 不同小版本里，NMSBoxes 的返回值从 (N,) 变成 (N,1) 又变回 (N,)。reshape(-1) 吃掉这个差异。跨版本调用要防御返回 shape 变化，这在嵌入式部署里是常态。

4.6 检测结果排序 ​

python
detections.sort(key=lambda item: (item["pixel"][1], item["pixel"][0], item["class_id"]))

按 (v, u, class_id) 排序就是先按行、再按列。这是扫描线的顺序，让下游的机械臂路径尽量单调（详见第四篇）。

排序放在检测函数内部，而不是留给调用方：产出就该是可直接消费的顺序，这样每个调用方都不会忘记排。

五、一个隐性畸变：输入 736 而相机 720 ​

python
YOLO_INPUT_WIDTH  = 1280
YOLO_INPUT_HEIGHT = 736
YOLO_EXPECTED_IMAGE_WIDTH  = 1280
YOLO_EXPECTED_IMAGE_HEIGHT = 720

736 / 720 = 1.022，纵向被拉伸了 2.2%。

为什么中心点还行？因为 resize 模式下 scale_y = 736/720，反变换时除以它就能精确还原中心点的像素坐标：

v_original = (v_input - pad_y) / scale_y = v_input * 720 / 736

但有两个隐患：

  • 框的形状在推理时被纵向压缩 2.2%，模型看到的物体比例与训练分布不完全一致，可能影响召回率，尤其是细长目标。
  • 如果训练侧也用 736，那训练时的标签也是按同样拉伸算的，两边一致就没问题。关键是两侧一致，数值本身是否“正确”反而是次要的。

所以代码单独保留了 YOLO_EXPECTED_IMAGE_* 这组期望值，用于校验相机实际出图尺寸：

python
if image.shape[1] != cfg.YOLO_EXPECTED_IMAGE_WIDTH or \
   image.shape[0] != cfg.YOLO_EXPECTED_IMAGE_HEIGHT:
    # 相机换了分辨率，预处理参数需要重新确认

这类“不致命但会慢慢偏”的细节必须有显式常量记录，否则半年后没人知道 736 是故意的还是打错了，而看起来不规整的数字最容易被后来的人顺手改回 720。

六、红绿灯检测：把颜色问题变成形态学问题 ​

巡检的判定目标是「指示灯是否亮着红灯」。看似是颜色问题，实际上是「红色物体」和「亮着的红灯」的区分问题。

6.1 HSV 双区间：红色跨了色环 ​

python
def build_red_mask(image_bgr):
    hsv = cv2.cvtColor(image_bgr, cv2.COLOR_BGR2HSV)

    lower1 = np.array([cfg.RED_HUE_LOW_1,  cfg.RED_MIN_SATURATION, cfg.RED_MIN_VALUE], np.uint8)
    upper1 = np.array([cfg.RED_HUE_HIGH_1, 255, 255], np.uint8)
    lower2 = np.array([cfg.RED_HUE_LOW_2,  cfg.RED_MIN_SATURATION, cfg.RED_MIN_VALUE], np.uint8)
    upper2 = np.array([cfg.RED_HUE_HIGH_2, 255, 255], np.uint8)

    mask = cv2.bitwise_or(
        cv2.inRange(hsv, lower1, upper1),
        cv2.inRange(hsv, lower2, upper2),
    )
    mask = cv2.medianBlur(mask, 3)
    kernel = np.ones((3, 3), dtype=np.uint8)
    mask = cv2.morphologyEx(mask, cv2.MORPH_CLOSE, kernel, iterations=1)
    mask = cv2.dilate(mask, kernel, iterations=1)
    return mask, hsv

OpenCV 的 H 范围是 0–179（8 位量化），红色落在两段：0–10 和 170–179。

只写一段的后果：漏掉一半红色。更隐蔽的是，如果只写 0–10，偏紫的红（H≈175）就会被判为不属于红色，而人眼看起来毫无区别。

6.2 三重强度条件 ​

python
def find_red_components(mask, hsv):
    count, labels, stats, centroids = cv2.connectedComponentsWithStats(mask, 8)
    components = []
    value = hsv[:, :, 2]

    for idx in range(1, count):                  # 0 是背景
        area = int(stats[idx, cv2.CC_STAT_AREA])
        if area < cfg.RED_MIN_AREA_PX:           # 700 px
            continue

        comp_mask = labels == idx
        max_value  = int(value[comp_mask].max())
        mean_value = float(value[comp_mask].mean())
        if max_value < cfg.RED_MIN_MAX_VALUE or mean_value < cfg.RED_MIN_MEAN_VALUE:
            continue                              # 都是 248

        x = int(stats[idx, cv2.CC_STAT_LEFT])
        y = int(stats[idx, cv2.CC_STAT_TOP])
        width  = int(stats[idx, cv2.CC_STAT_WIDTH])
        height = int(stats[idx, cv2.CC_STAT_HEIGHT])
        cx, cy = centroids[idx]

        components.append({
            "area_px": area,
            "bbox": [x, y, width, height],
            "centroid": [float(cx), float(cy)],
            "max_value": max_value,
            "mean_value": mean_value,
        })

    components.sort(key=lambda item: item["area_px"], reverse=True)
    return components

6.3 为什么每个阈值都必要 ​

条件值过滤掉什么为什么不能省
S ≥150灰白、米色的红色系物体低饱和的红是“染色”，不是“发光”
V ≥248（max 与 mean 都要）深红、暗红、背光下的红只有自发光才能到 248+
area ≥700 px噪点、远处小红点640×480 下 700 px ≈ 30×23
medianBlur(3)—椒盐噪点低照度下 RGB 噪点明显
MORPH_CLOSE3×3灯珠被细线切断指示灯常有不规则反光罩

max_value 与 mean_value 同时约束，是这段实现里最巧的一处：

  • 只有 mean：一个大暗区里有一个极小亮点 → mean 不达标，但那个点其实是真的亮着；
  • 只有 max：单个噪点就能通过 → 误报；
  • 两者都要：既保证「确实存在极亮点」，又保证「整个连通域都亮」。

这是典型的「必要条件叠加」：每个条件单独都太松，叠加起来刚好。前提是这些条件在物理上是独立的（饱和度、亮度、面积分别对应不同物理量），不是在同一个量上重复设阈。

同时带上 algorithm 版本号（hsv_red_connected_components_v1），这是结果可追溯的最小成本方案。换成 v2 算法时，历史数据仍然知道自己是被哪个版本判定的。

6.5 调试图的判别力 ​

python
def make_debug_image(image_bgr, components, red_detected):
    debug = image_bgr.copy()
    color = (0, 0, 255) if red_detected else (0, 180, 255)
    for comp in components:
        x, y, width, height = comp["bbox"]
        cv2.rectangle(debug, (x, y), (x + width, y + height), color, 2)
        cv2.putText(debug, f"red {comp['area_px']}", (x, max(16, y - 6)),
                    cv2.FONT_HERSHEY_SIMPLEX, 0.5, color, 1, cv2.LINE_AA)
    label = "ABNORMAL red light" if red_detected else "NORMAL no red light"
    cv2.putText(debug, label, (12, 28), cv2.FONT_HERSHEY_SIMPLEX, 0.8, color, 2, cv2.LINE_AA)
    return debug

调试图不只是「画个框」，它承载了三层信息：

  1. 框在哪：位置对不对；
  2. 面积多大：阈值是否合适，数字直接写在框上方；
  3. 整体判定：大字号贴在左上角，扫一眼就知道结论。

调试输出最好能在一张图里回答尽量多的问题。出问题时最贵的成本是「再跑一次采样」，所以能塞多少判别信息就塞多少。

七、离线验证器：把「模型好不好」和「机器人能不能动」解耦 ​

系统里有一个独立的验证网页/CLI，不依赖 ROS、可在开发机上运行：上传图片 → 可视化检测框 → 置信度统计 → 与标注比对。

它的设计价值在于解耦：

问题需要什么验证器能否回答
模型检不出目标一张图 + 模型能
置信度阈值是否合适一批图 + 统计能
预处理是否配错一张图 + 肉眼对比能
机械臂动得对不对整套硬件 + 现场不能

把能离线判定的部分全部离线化，现场调试时间能压缩一个数量级。现场最贵的是「人、机器、场地同时在位」的时间，而不是算力。

八、小结 ​

检测这套工程的五条：

  1. 后端默认 auto，先试强的、失败退回一定能跑的，且降级必须留日志；
  2. 预处理模式是配置项，必须与训练逐字一致，差值全为 0 才算对齐；
  3. 输出布局靠启发式适配，但类别数已知时走确定性分支，并且导出后必须肉眼验一张；
  4. 长宽比畸变不致命但会慢慢偏，用显式期望值常量锁住，防后来者“顺手改回”；
  5. 颜色判定要用条件叠加，且各条件对应物理上独立的量，单阈值永远在漏检和误报之间摆动。
